# シナリオの隔離と追加

WireMock のシナリオを名前で選ぶ方法、テストごとのリセット、シナリオの追加手順、並列実行の禁止を説明する。
検査の入口は `tests/m07-scenario-isolation.sh`（`unit` と `smoke`）。
名前と宛先の解決、リセットと確認は `scripts/scenario-lib.sh` にある。

## シナリオ一覧

| 名前 | パス | 応答 | マッピングのファイル |
| --- | --- | --- | --- |
| `normal` | `/api/users/123` | 200 と JSON 本文 | `normal-case.json` |
| `error-500-then-200` | `/api/error-500-then-200` | 1回目は 500、2回目以降は 200（状態を持つ） | `error-500-then-200-1.json`、`error-500-then-200-2.json` |
| `ratelimit-429` | `/api/ratelimit` | 429 と `Retry-After: 2` | `error-429-case.json` |
| `slow-100` | `/api/slow-100` | 100ミリ秒遅延の 200 | `delay-100ms-case.json` |
| `slow-5000` | `/api/slow-5000` | 5000ミリ秒遅延の 200 | `delay-5000ms-case.json` |

名前から宛先のパスを引くには、次のように呼ぶ。未定義の名前は終了コード 2 で止まり、定義済みの名前一覧を出す。

```sh
. scripts/scenario-lib.sh
scenario_path normal
```

## シナリオの追加手順

アプリケーションのコードは変えない。次の手順で、JSON ファイルを1つ足す。

1. 置き場所を決める。マッピングは `wiremock-scenarios/mappings/` に1ファイル1マッピングで置く。
   応答の本文は `wiremock-scenarios/__files/` に置き、`response.bodyFileName` で参照する。既存の本文を使い回してよい。
2. 必須項目を書く。`name`、`request.method`、`request.urlPath`、`response.status` が必要。
   `name` は `^[a-z0-9][a-z0-9-]*$` の形式にする。同じ `name` は、同じ `method` と `urlPath` に限って複数のファイルに現れてよい。
3. 状態を持つシナリオは、状態ごとに1ファイルにする。
   `scenarioName` を揃え、`requiredScenarioState` に今の状態、`newScenarioState` に次の状態を書く。
   最後の状態では `newScenarioState` を省く。開始状態の `Started` を持つのは1ファイルだけにする。

検証は、名前の解決と静的検査が通ることを確かめる。

```sh
. scripts/scenario-lib.sh
scenario_path <名前>
scenario_check_static
```

反映は、ファイルを足した後に `POST /__admin/reset` を呼ぶ。コンテナの再起動は要らない。

状態を持たないシナリオの例は次のとおり。`name` が一意で、`urlPath` が既存の宛先と重ならないことを確かめる。

```json
{
  "name": "example-added",
  "request": {
    "method": "GET",
    "urlPath": "/api/example-added"
  },
  "response": {
    "status": 200,
    "body": "example",
    "headers": {
      "Content-Type": "text/plain"
    }
  }
}
```

## リセットと確認

テストは、開始前と終了後に WireMock を初期状態へ戻す。失敗したテストも、後始末でリセットを試みる。
リセットは `POST /__admin/reset` の1回で行う。この呼び出しで、マッピング、リクエストジャーナル、シナリオ状態が戻る。
管理APIで足したマッピングは消え、`mappings/` のファイルは残る。コンテナの再起動は使わない。

リセット後は次の3項目を確かめる。どれかが外れたら、項目名と期待値と実測値を標準エラーへ出して止まる。

| 項目 | 期待値 |
| --- | --- |
| マッピングの件数 | `mappings/*.json` のファイル数（`.gitkeep` を除く） |
| リクエストジャーナルの件数 | 0 |
| シナリオの状態 | すべて `Started` |

Squid のキャッシュは無効にしている（`squid-config/squid.conf` の `cache deny all`）。
キャッシュがあると、WireMock の状態の変化が古い応答で隠れ、リセット後の結果が毎回同じにならない。

## 並列実行をしない理由

1台の WireMock に対して、複数のテストを並列に実行しない。
次の状態は WireMock と実行環境で共有されるため、並列に走らせるとテストが互いの結果を壊す。

| 共有されるもの | 並列時の影響 |
| --- | --- |
| シナリオ状態 | 一方のリクエストが「500の後に200」の状態を進め、他方の初回が 200 になる |
| リクエストジャーナル | 件数を数える検査が、他方の呼び出しも数える |
| リセット操作 | 一方のリセットが、他方の実行中のマッピングと状態を消す |
| ポートとコンテナ | Compose はポート 3128 と 8080 を固定で公開する。後始末の `down` が他方のコンテナも落とす |

テストは1つずつ実行する。並列に走らせる場合は、WireMock とポートを分けるなど、別の環境を用意する。

## 後始末

テストの終了時は、次の順で後始末する。失敗時も同じ順で行う。

1. リセットを試みる。結果を標準エラーに1行で出す（`cleanup: reset attempted`）。失敗しても続ける。
2. `docker-compose down --remove-orphans` でコンテナを止める。
3. 一時ディレクトリを削除する。

中断（`INT` と `TERM`）でも、同じ後始末を行う。終了コードは元の値を保つ。
