# テスト方式

このリポジトリのテストは、E2E だけである。ECS のエミュレータ（fakecloud）で、完成版のタスク定義を `run-task` して動かし、
Client から Squid、WireMock への実通信で、リトライとタイムアウトを確かめる。構成は [アーキテクチャ](../ARCHITECTURE.md) を参照。

## 方針

| 項目 | 内容 |
| --- | --- |
| 単位 | Client を1回実行するごとに、タスクを1つ起動する。Squid は毎回、起動し直す |
| 通信 | 実通信。Client は、Squid の別名 `swsc-squid:3128` 経由で WireMock に届く |
| 範囲外 | 単体テスト、スクリプトの中身を読む検査。ビジネスロジックのテストは、必要になったときに足す |
| AWS | CI は AWS に接続しない。AWS での確認は、利用者が手動で行う（[AWS での確認](#aws-での確認)） |

## 実行方法

前提は [アーキテクチャ](../ARCHITECTURE.md) の「実行環境の前提」を参照。初回だけ、検査ツールを固定版で入れる。

```bash
mise install --locked
```

```bash
npm run test:ci                                                              # 起動、検査、収集、停止を続けて実行する
sh scripts/e2e.sh test:ci normal error-500-then-200 ratelimit-429 slow-5000  # 4シナリオ（CI と同じ）
sh scripts/e2e.sh test:ci error-500-then-200                                 # 1シナリオだけ
```

名前は、既定の順と違う順で指定してよい。実行は常に直列である。1つずつ操作するときは、次のコマンドを使う。

| コマンド | 内容 |
| --- | --- |
| `npm run start` | WireMock、レジストリ、fakecloud を起動し、タスク定義を登録する |
| `npm run test` | タスクを起動して Client を実行し、基本の3項目を検査する |
| `npm run logs` | 基盤（fakecloud、WireMock、レジストリ）のコンテナのログを表示する |
| `npm run stop` | 起動したコンテナとネットワークを削除する |
| `npm run clean` | `stop` に加えて、ビルドしたイメージ、生成物、収集ログを削除する |

- 固定ポート 8080（WireMock）、14566（fakecloud）、15000（レジストリ）は、入口のロック（既定は `/tmp/swsc-e2e-ports.lock`）で
  1つの実行だけに限る。別のスタックが同じポートを使っているときは実行しない。
- 失敗したときは、`e2e-logs/` に収集したログが残る。Squid と Client のログは、タスクごとに消えるため、この収集物で読む。

### 終了コード

| 終了コード | 意味 |
| --- | --- |
| 0 | 全件合格 |
| 1 | 一つでも失敗した。リセット確認の失敗による未実行を含む |
| 2 | 引数の誤り。未定義または対象外のシナリオ名 |
| 130、143 | 実行中に `INT` または `TERM` を受けた。後始末の後に終了する |

## 検査の内容

### 基本の3項目（`npm run test:ci`）

| 項目 | 内容 | 期待 |
| --- | --- | --- |
| 1 許可ドメイン | `http://api.example.com` を叩く | `CLIENT_STATUS=200`、WireMock の受信数 1 |
| 2 許可外ドメイン | `http://blocked.example.net` を叩く | `CLIENT_STATUS=403`、WireMock の受信数 0 |
| 3 Squid 再起動後 | Squid を再起動し、同じタスクのネットワークで Client を追加で実行する | `CLIENT_STATUS=200`、WireMock の受信数 1 |

3 の追加の Client は、タスクの Client が1回で終わるために使う。ECS を通らない。

### 代表4シナリオ

| シナリオ | パス | 上書きする設定 | status | result | attempts | retries | wiremock | rc |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| `normal` | `/api/users/123` | なし | 200 | success | 1 | 0 | 1 | 0 |
| `error-500-then-200` | `/api/error-500-then-200` | なし | 200 | success | 2 | 1 | 2 | 0 |
| `ratelimit-429` | `/api/ratelimit` | なし | 429 | retries_exhausted | 4 | 3 | 4 | 0 |
| `slow-5000` | `/api/slow-5000` | `RESPONSE_TIMEOUT_SECONDS=1` | -（出力なし） | timeout | 1 | 0 | 1 | 28 |

- status は標準出力の `CLIENT_STATUS` の値である。`slow-5000` は応答を受けないため `-` になる。
- attempts は総試行、retries はリトライ回数である。retries は attempts から 1 を引いた値に等しい。
- wiremock は、WireMock のジャーナルに残ったそのパスへの受信回数である。
- rc は Client の終了コードである。`ratelimit-429` は再試行を使い切っても終了コード 0 になる。

#### レポートの見方

レポートは標準出力に出る。1シナリオにつき1行で、シナリオ名、期待値、実測値、合否を並べる。

```text
scenario | expected | actual | result
normal | status=200 result=success attempts=1 retries=0 wiremock=1 rc=0 | status=200 ... | PASS
summary: PASS passed=4 failed=0 not_run=0 failed_scenarios=- elapsed=10s
```

最後の行（`summary:`）は全体の合否、合格と失敗と未実行の件数、失敗したシナリオ名、秒数を示す。

#### 失敗時の見方

シナリオが失敗すると、標準エラーに `scenario:`（名前）、`path:`、`overrides:`、`expected:`、`actual:`、
`rerun:`（そのシナリオだけを再実行するコマンド）、`diag:`（Client の診断ログ）が出る。診断ログに認証情報は含まれない。

リセット確認が外れた場合は、`FAIL: リセットを確認できないため <名前> を実行しない` と出る。
その後のシナリオは `NOT_RUN` になる。最初に見るべきはリセットの結果である。

## WireMock のシナリオ

実行は `scripts/e2e-scenarios.sh`、名前からパスを引く処理とリセットは `scripts/scenario-lib.sh` にある。

### 一覧

| 名前 | パス | 応答 | マッピングのファイル |
| --- | --- | --- | --- |
| `normal` | `/api/users/123` | 200 と JSON 本文 | `normal-case.json` |
| `error-500-then-200` | `/api/error-500-then-200` | 1回目は 500、2回目以降は 200（状態を持つ） | `error-500-then-200-1.json`、`error-500-then-200-2.json` |
| `ratelimit-429` | `/api/ratelimit` | 429 と `Retry-After: 2` | `error-429-case.json` |
| `slow-100` | `/api/slow-100` | 100ミリ秒遅延の 200 | `delay-100ms-case.json` |
| `slow-5000` | `/api/slow-5000` | 5000ミリ秒遅延の 200 | `delay-5000ms-case.json` |

名前から宛先のパスを引くには、次のように呼ぶ。未定義の名前は終了コード 2 で止まり、定義済みの名前一覧を出す。

```sh
. scripts/scenario-lib.sh
scenario_path normal
```

### 追加の手順

アプリケーションのコードは変えない。次の手順で、JSON ファイルを1つ足す。

1. 置き場所を決める。マッピングは `wiremock-scenarios/mappings/` に1ファイル1マッピングで置く。
   応答の本文は `wiremock-scenarios/__files/` に置き、`response.bodyFileName` で参照する。既存の本文を使い回してよい。
2. 必須項目を書く。`name`、`request.method`、`request.urlPath`、`response.status` が必要。
   `name` は `^[a-z0-9][a-z0-9-]*$` の形式にする。同じ `name` は、同じ `method` と `urlPath` に限って複数のファイルに現れてよい。
3. 状態を持つシナリオは、状態ごとに1ファイルにする。
   `scenarioName` を揃え、`requiredScenarioState` に今の状態、`newScenarioState` に次の状態を書く。
   最後の状態では `newScenarioState` を省く。開始状態の `Started` を持つのは1ファイルだけにする。

検証は、名前の解決と静的検査が通ることを確かめる。

```sh
. scripts/scenario-lib.sh
scenario_path <名前>
scenario_check_static
```

反映は、ファイルを足した後に `POST /__admin/reset` を呼ぶ。コンテナの再起動は要らない。
状態を持たないシナリオの例は次のとおり。`name` が一意で、`urlPath` が既存の宛先と重ならないことを確かめる。

```json
{
  "name": "example-added",
  "request": {
    "method": "GET",
    "urlPath": "/api/example-added"
  },
  "response": {
    "status": 200,
    "body": "example",
    "headers": {
      "Content-Type": "text/plain"
    }
  }
}
```

### リセットと確認

テストは、開始前と終了後に WireMock を初期状態へ戻す。失敗したテストも、後始末でリセットを試みる。
リセットは `POST /__admin/reset` の1回で行う。この呼び出しで、マッピング、リクエストジャーナル、シナリオ状態が戻る。
管理 API で足したマッピングは消え、`mappings/` のファイルは残る。コンテナの再起動は使わない。

リセット後は次の3項目を確かめる。どれかが外れたら、項目名と期待値と実測値を標準エラーへ出して止まる。

| 項目 | 期待値 |
| --- | --- |
| マッピングの件数 | `mappings/*.json` のファイル数（`.gitkeep` を除く） |
| リクエストジャーナルの件数 | 0（Squid の内部要求を除く） |
| シナリオの状態 | すべて `Started` |

Squid は、自分の内部要求（`/squid-internal-periodic/store_digest` など）を WireMock へ散発的に送り、ジャーナルに残る。
これはテストの通信ではないため、URL が `/squid-internal-` で始まる要求は、ジャーナルの件数に数えない。
それ以外の要求が1件でも残れば失敗とする。`meta.total` と `requests[]` の件数が一致しないときは、数えられないので失敗とする。

Squid のキャッシュは無効にしている（`squid-config/squid.conf` の `cache deny all`）。
キャッシュがあると、WireMock の状態の変化が古い応答で隠れ、リセット後の結果が毎回同じにならない。

### 並列実行をしない理由

1台の WireMock に対して、複数のテストを並列に実行しない。
次の状態は WireMock と実行環境で共有されるため、並列に走らせるとテストが互いの結果を壊す。

| 共有されるもの | 並列時の影響 |
| --- | --- |
| シナリオ状態 | 一方のリクエストが「500の後に200」の状態を進め、他方の初回が 200 になる |
| リクエストジャーナル | 件数を数える検査が、他方の呼び出しも数える |
| リセット操作 | 一方のリセットが、他方の実行中のマッピングと状態を消す |
| ポートとコンテナ | 8080、14566、15000 は固定で、同じ名前のコンテナを使う。後始末の停止が他方の資源も消す。入口のロックで1実行ずつに限る |

並列に走らせる場合は、WireMock とポートを分けるなど、別の環境を用意する。

## AWS での確認

AWS の E2E では、WireMock を使わず、公開されたテスト用 API の `httpbin.org` を HTTPS で叩く。CI は AWS に接続しない。
デプロイの手順は [AWS へのデプロイ](AWSへのデプロイ.md) を参照。

httpbin.org は、HTTP のリクエストとレスポンスを確かめるための、公開されたテスト用サービスである。
オープンソースで、認証なしで使える。指定したステータスコードや遅延で応答を返せるため、Client のリトライとタイムアウトの確認に向く。

| 環境 | 叩く先 | プロトコル |
| --- | --- | --- |
| ローカル、CI | WireMock（`api.example.com` の名前で転送） | HTTP |
| AWS | `httpbin.org` | HTTPS |

| パス | 動作 | 使いどころ |
| --- | --- | --- |
| `/status/200` | 200 を返す | 正常系 |
| `/status/500` | 500 を返す | 5xx のリトライを使い切る確認 |
| `/status/429` | 429 を返す | 429 のリトライを使い切る確認 |
| `/delay/5` | 5 秒待ってから 200 を返す | タイムアウトの確認 |
| `/get` | 受け取ったリクエストの内容を JSON で返す | プロキシ経由の疎通 |

- Squid は HTTPS を `CONNECT` で中継する。API が返した 500 や 429 は Squid のログに残らず、Client のログ（`CLIENT_STATUS`、`CLIENT_DIAG`）で確認する。
- 公開サービスなので、可用性の保証はない。混んでいるときは 502 や 503 を返すことがある。負荷をかけず、少ない回数の要求にとどめる。
- 認証情報や、実データを含む要求を送らない。
- `/status/500` は毎回 500 を返す。「500 の後に 200」は再現できないため、`error-500-then-200` の確認は WireMock で行う。
- `/delay/{秒}` の上限は 10 秒。
- 別のドメインを使うときは、`squid-config/whitelist.txt` に足してイメージを作り直す。

2026-11-12 の確認結果は、[仕様](../specs/MVP/spec.md) に記録している。

## CI（`.github/workflows/e2e-test.yml`）

PR と push で、次の順に実行する。同じ検査は [AGENTS.md](../AGENTS.md) にあり、コミット前に手元でも実行する。

| step | 内容 | 上限 |
| --- | --- | --- |
| shellcheck | 全 `.sh` を `-s sh -S style` で検査する | 3 分 |
| actionlint | ワークフローを検査する | 2 分 |
| gitleaks | 識別情報の値を検出する（`.gitleaks.toml`、値は出さない） | 2 分 |
| cdk-install | `npm ci --prefix cdk --ignore-scripts` | 3 分 |
| cdk-synth | `cdk synth`（AWS に接続しない） | 3 分 |
| check-cdk | `synth` の出力が、`render` の本番用の出力と一致するか | 1 分 |
| test-ci | `npm run test:ci` と、4シナリオの `test:ci` | 10 分 |
| collect / upload | 失敗時に収集したログを成果物に上げる | - |
| stop | 残ったコンテナを必ず消す | - |

CI では Secrets を使わない。実 AWS には接続しない。アクションは、コミット SHA で固定する。

## 後始末

テストの終了時は、次の順で後始末する。失敗時も同じ順で行う。

1. リセットを試みる。結果を標準エラーに1行で出す（`cleanup: reset attempted`）。失敗しても続ける。
2. `docker rm -f` で、タスクのコンテナとネットワークを消す。対象は、起動したタスクの ID（`fakecloud-ecs-task` ラベル、
   `fakecloud-ecs-<ID>` のネットワーク）に限る。
3. `docker rm -f` で、基盤のコンテナ（fakecloud、レジストリ、WireMock、追加の Client）を消す。対象は、接頭辞 `swsc-` と
   ラベル `swsc.managed=true` の両方に一致するものだけである。レジストリ用のイメージのタグも消す。
4. 一時ディレクトリを削除する。
5. 入口のロックを解放する。ロックを取ったのが単独の入口の場合だけ行う。

中断（`INT` と `TERM`）でも、同じ後始末を行う。終了コードは元の値を保つ。
`docker stop` は使わない。Squid の元のエントリポイントは SIGTERM を転送しないため、止まらないからである。
