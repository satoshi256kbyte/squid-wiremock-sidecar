# ポート公開範囲

ローカル実行（ECS タスク定義方式）で、ホストへ公開するポートとその公開先を説明する。

## 概要

WireMock（8080番）だけを、ホストの `127.0.0.1` に公開する。
同じホストで動くテストクライアントやブラウザからは接続できる。
Squid（3128番）はホストへ公開しない。pause コンテナと共有する namespace の中だけで待ち受ける。
他のホストや別マシンからは、この設定では接続できない。

## 接続先

| 対象 | 接続先 | 用途 |
| --- | --- | --- |
| WireMock | `127.0.0.1:8080`（ホスト） | モックの応答。管理API（`/__admin`）も同じ公開範囲で到達できる |
| Squid プロキシ | `127.0.0.1:3128`（pause の namespace の中だけ） | HTTP プロキシ。許可ドメインだけを WireMock へ転送する |

Test Client は、pause の namespace を Squid と共有する。`127.0.0.1:3128` で Squid を使う。
この経路はホストへ出ない。Client から送る要求は、Client の中で proxy を指定して送る。

公開の設定は次のとおり。`scripts/e2e-runner.sh` が WireMock を起動するとき、次の指定で公開する。
ホストIPを `127.0.0.1` と明示して、公開先がホストの外へ広がらないようにしている。

```text
-p 127.0.0.1:8080:8080
```

IPv6 の `::1` は公開しない。`localhost` は環境によって `::1` へ解決されるため、接続先は `127.0.0.1` と書く。

設定が正しいことは、次の手順で確かめられる。

```sh
sh scripts/e2e.sh start
docker ps --filter label=swsc.managed=true --format '{{.Names}} {{.Ports}}'
curl --silent --output /dev/null --write-out '%{http_code}\n' http://127.0.0.1:8080/__admin/mappings
sh scripts/e2e.sh stop
```

`unit` は Docker を使わずに、公開の設定の文字列を判定する。
`docker ps` の出力で、8080 の欄が `127.0.0.1:8080->8080/tcp` になり、`0.0.0.0` や `::` を含まないことを確かめる。
Squid の 3128 の欄は出ないことも確かめる。最後のコマンドは `200` を返す。

## Squid の送信元制御

Squid は、送信元が次の範囲にある要求だけを許可ルールに通す。

| 範囲 | 意味 |
| --- | --- |
| `127.0.0.0/8` | ループバック。ホストから `127.0.0.1` 経由で届く要求 |
| `10.0.0.0/8` | RFC 1918 の私設範囲 |
| `172.16.0.0/12` | RFC 1918 の私設範囲。Docker の既定のブリッジ（`172.17.0.0/16`）を含む |
| `192.168.0.0/16` | RFC 1918 の私設範囲 |

範囲外の送信元からの要求は、`http_access deny all` で拒否される。

`sidecar` ネットワークのサブネットは固定しない。Docker は起動のたびに空いているサブネットを割り当てるため、
固定すると既存の環境と衝突するおそれがある。範囲を RFC 1918 の全体にすれば、固定しなくても Test Client の要求を受けられる。
Docker の `default-address-pools` を RFC 1918 の外へ設定した環境では、要求が範囲外になるため拒否される（後述の「症状と対処」）。

## 許可ネットワークを採用しない理由

ループバック以外の端末から Squid や WireMock へ接続できる許可ネットワークの設定は採用しない。
利用者は 2026-11-03 に、この既定を承認した。

採用しない理由は次のとおり。

- 既存の README と検査は、すべてホストの `127.0.0.1` か `localhost` から接続する。別ホストから使う手順も検査もない。
- 許可ネットワークを設定項目にすると、誤設定で全インターフェースの公開へ戻せてしまう。
- 採用すると、範囲の指定方法と、その検査を保守する費用が増える。利用の実態がない範囲に、その費用は見合わない。

検討して採用しなかった案は次のとおり。

| 案 | 採用しなかった理由 |
| --- | --- |
| 環境変数でホストIPを指定する | 誤設定で全インターフェースの公開へ戻せる。検査が環境に依存する |
| 起動用の override 設定で許可範囲を足す | 利用の実態がなく、検査の保守費用が見合わない |
| `::1` も公開する | 公開面が増えるが、利点がない |

次の運用が必要になった場合は、この決定を見直す。LAN 上の別端末や、リモートの CI ランナーから、
この基盤のプロキシへ直接接続する運用である。その時点で、許可範囲の指定方法と検査を追加し、本書を更新する。

## 別マシンや別コンテナから使う場合

別マシンからは、ホストの `127.0.0.1` に届かないため直接接続できない。
別マシンから使う必要があるときは、利用者側で SSH のポートフォワードを使う。

```sh
ssh -N -L 8080:127.0.0.1:8080 <REMOTE_USER>@<REMOTE_HOST>
```

この例では、利用者の端末の `127.0.0.1:8080` が、遠隔ホストの同じポートへ転送される。
Squid の 3128 は遠隔ホストでもホストへ公開していないため、この方法では転送できない。
Squid を使う要求は、pause の namespace に入るコンテナ（Client）から送る。

## 症状と対処

| 症状 | 原因 | 対処 |
| --- | --- | --- |
| 別マシンや別コンテナから接続が拒否される、またはタイムアウトする | 公開先がホストの `127.0.0.1` だけのため | SSH のポートフォワードなど、利用者側の手段を使う（前節） |
| `localhost` への接続が失敗する | 一部のクライアントは `localhost` を `::1` へ解決する。`::1` は公開していない | 接続先を `127.0.0.1` に直す |
| 許可ドメインの要求が HTTP 403 になる | Docker が `default-address-pools` で RFC 1918 の外のサブネットを割り当て、送信元が ACL の範囲外になった | `squid-config/squid.conf` の `acl local_src` に、そのサブネットを追加する |
| ホストから `127.0.0.1:3128` へ接続できない | Squid はホストへ公開していない | Client の経路（pause の namespace の中）から送る。ホストから使う手段は用意していない |
| 起動時にポート 8080 が使用中で失敗する | 別のプロセスが同じポートを使っている | そのプロセスを止める。ホストIPを変える設定は用意していない |
