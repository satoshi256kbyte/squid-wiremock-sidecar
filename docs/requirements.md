# ECS サイドカープロキシを利用した HTTP クライアント E2E テスト基盤

検証環境構築要件定義書

## 1. プロジェクト概要

AWS ECS（Elastic Container Service）上で稼働する外部 API 連携システムにおいて、
本番同等のプロキシ（サイドカー）構成を維持したまま、完全にネットワークが閉じた状態で
正常系および異常系の E2E テストを実施できるサンドボックス環境を構築する。

## 2. 背景と目的

HTTP クライアントの堅牢性を担保するためには、
相手先サーバーからのエラー応答（500, 503 等）や通信遅延に対する
リトライ制御・フェイルオーバーが正しく機能するかを検証する必要がある。

本プロジェクトでは、ECS のタスク定義におけるサイドカーパターンをローカル（Ministack 等）
および CI 環境でエミュレーションし、安全かつ再現性の高い障害シミュレーション環境を提供する。

## 3. システム構成要件

本環境は以下の 3 つの主要コンポーネントで構成される。

### 3.1 Test Client（テスト対象アプリ）

- ECS タスク内のメインコンテナ
- 環境変数等で同一タスク内のプロキシ（サイドカー）を指定
- 外部 API 宛ての通信を行う

### 3.2 Proxy（Squid サイドカー）

- Client と同一の ECS タスク内で稼働
- awsvpc ネットワークモードにより localhost を共有
- リクエストをインターセプト
- 特定のターゲットドメイン宛ての通信をインターネットではなく
  同一ネットワーク内の Mock Server へ強制ルーティング

### 3.3 Mock Server（WireMock）

- 別タスク（または独立したコンテナ）として稼働
- 外部 API の振る舞いを擬似化
- 事前に定義されたシナリオに従い、正常なレスポンスや
  意図的なエラー・遅延を返却

## 4. 機能要件

| 要件 | 説明 |
|------|------|
| ECS サイドカー構成の完全再現 | awsvpc モードにおけるタスク内の localhost 通信をローカル環境でエミュレーションし、本番のタスク定義モデルを忠実に再現できること |
| 閉域ルーティング（Proxy Intercept） | プロキシの許可リストと設定（cache_peer 等）によって、特定の外部ドメイン宛ての通信を Mock Server へ転送し、許可外のドメイン宛ての通信を拒否できること。プロキシを使わない直接接続の遮断は保証しない |
| 異常系シミュレーション | Mock Server 側で、任意の HTTP ステータスコード（429, 500, 503 等）の返却、および指定ミリ秒のレスポンス遅延（タイムアウト検証用）を発生させられること |
| 振る舞いのコード化 | Mock Server が応答するシナリオ（URL パス、メソッド、返却データ、エラー条件）を JSON 等で定義できること |

## 5. 非機能要件

| 要件 | 説明 |
|------|------|
| ポータビリティ（移植性） | 開発者のローカル PC、および CI/CD パイプライン上で、コマンド一つでコンテナの構築からテスト実行、環境破棄までが完結すること |
| IaC（Infrastructure as Code） | コンテナおよびネットワークの構成要素がすべてコード管理され、本番の ECS タスク定義と互換性のある形（ECS タスク定義のテンプレート等）で記述されていること |
| メンテナンス性 | Proxy のルーティングルールや Mock のレスポンス定義が、外部ファイルとしてマウントされ容易に更新・追加できる設計であること |

## 6. 前提技術スタック

- **Local Emulation**: ECS タスク定義方式（`docker run` と pause 共有 namespace。Ministack/LocalStack 等）
- **Container Orchestration（本番）**: AWS ECS（Fargate または EC2）、awsvpc ネットワークモード
- **Proxy**: Squid（OSS フォワードプロキシ）
- **Mock Server**: WireMock
- **IaC & Automation**: ECS タスク定義（テンプレートから生成）、Shell Scripts、AWS CLI

## 8. 制約事項

- Squid のルーティングは localhost:3128 を通すため、
  クライアント側のプロキシ設定（HTTP_PROXY 環境変数等）が必須
- WireMock は REST API でスタブ定義の動的変更をサポート
- Docker の実行環境が必須（ローカル・CI 共通）。Docker Compose は使わない
