# M06 Test Clientのリトライとタイムアウトの仕様

## 1. 目的

Test Clientに、一時的なサーバー障害とレート制限を再現可能に扱うリトライ、バックオフ、タイムアウトを追加する。
成功応答は余分なリトライなしで返し、失敗時は回数、待機時間、最終結果を診断ログで追跡できるようにする。

## 2. 対象範囲

- HTTP 500と503に対する、設定回数までの指数バックオフ付きリトライ
- HTTP 429に対する専用の待機ポリシーと`Retry-After`ヘッダーの尊重
- 接続タイムアウトとレスポンスタイムアウト
- タイムアウト発生時の終端結果（終了コードと出力）の定義
- リトライ回数、待機時間、タイムアウトの環境変数による設定
- リトライ回数、待機時間、最終結果の診断ログ
- 境界値とリトライ対象外ステータスの単体レベル検証
- リトライ判定・待機計算の関数分離（`test-client/retry-lib.sh`）
- M04スモークテストの`/api/error-500`実行への待機0指定（`RETRY_BACKOFF_BASE_SECONDS=0`）の追加（clarify決定・要確認）

## 3. 機能要件

| ID | 要件 |
| --- | --- |
| FR-601 | HTTP 500と503を、設定されたリトライ回数まで指数バックオフで再試行する |
| FR-602 | HTTP 429は500/503とは別の設定と待機ポリシーで扱う |
| FR-603 | 429に`Retry-After`（秒数形式`^[0-9]+$`）があれば、その秒数を待機時間として使う。上限超過時は`RETRY_MAX_WAIT_SECONDS`へ切り詰めて待機しリトライを続ける（clarify決定・要確認）。`Retry-After: 0`は待機0秒で再試行し、リトライ回数は通常どおり消費する。HTTP日付、負数、空、小数、数字以外を含む値は存在しないものとして扱い、FR-604の既定待機を使う。判定は前後の空白とCRを除いた値で行い、先頭の0を除いた桁数が7桁以上の数字列は秒数形式に一致するため上限超過として扱い、`RETRY_MAX_WAIT_SECONDS`へ切り詰める。桁数の比較だけで判定し、算術には渡さない。診断ログのサーバー指定値は`retry_after=1000000`に飽和して出す。ヘッダー名は大文字小文字を区別せず、同名が複数あれば最後の値を使う。診断ログにサーバー指定値と実際の待機時間を出す |
| FR-604 | 429に`Retry-After`がない場合は、429専用の既定待機時間を使う。固定待機で指数的には増やさず、上限`RETRY_MAX_WAIT_SECONDS`を適用する（clarify決定） |
| FR-605 | 接続タイムアウト（`--connect-timeout`）とレスポンスタイムアウト（`--max-time`）を個別に設定できる |
| FR-606 | タイムアウト（curl終了コード28）で試行が失敗した場合、標準エラーへ`CLIENT_ERROR=timeout`を出力し、標準出力は空にして終了コード28で終了する。リトライはしない（clarify決定・要確認）。接続タイムアウトとレスポンスタイムアウトは出力で区別しない。curlの終了コードは診断ログに`curl_exit=28`として残す。接続拒否（7）など他のcurl失敗はM04どおり`curl_exit_<rc>`と終了コード`rc`とする |
| FR-607 | リトライ回数、バックオフ、タイムアウトを環境変数で設定できる。不正値は最初の通信前に検出し、標準エラーへ`CLIENT_ERROR=invalid_config`と`CLIENT_DIAG invalid_config name=<変数名>`（値は出さない）を出力して終了コード78で停止する。プロキシ未設定の検査（`proxy_not_configured`）を先に行い、両方不正なときは`proxy_not_configured`を優先する |
| FR-608 | 各試行について、試行番号、待機時間、理由を標準エラーへ診断ログとして出力する |
| FR-609 | 最終結果を診断ログに出力する。値は`success`、`retries_exhausted`、`timeout`の3種に固定する。リトライ対象ステータス（500、503、429）で終了した場合は常に`retries_exhausted`とする |
| FR-610 | 2xxなどリトライ対象外のステータスは、1回の試行でそのまま返す |
| FR-611 | リトライ上限到達時は最後のレスポンスの`CLIENT_STATUS`と`CLIENT_BODY`を出力し、終了コードは0とする（M04のHTTPエラー動作を維持、clarify決定・要確認）。リトライ回数0でも対象ステータスなら1回だけ試行して終了コード0とし、最終結果は`retries_exhausted`とする。非ゼロ終了はタイムアウト、curl失敗、プロキシ未設定、設定不備のみとする |

## 4. 設定

名称と既定値は次のとおり確定する（clarify決定）。
リトライは既定で有効とする（clarify決定・要確認）。
M04の`/api/error-500`は既定のままだと約7秒遅くなり、WireMockの呼び出し回数が1回から4回に増える。

| 環境変数 | 意味 | 既定値 |
| --- | --- | --- |
| `RETRY_MAX_ATTEMPTS_5XX` | 500/503の最大リトライ回数 | 3 |
| `RETRY_BACKOFF_BASE_SECONDS` | 500/503の初回待機秒数（以降は2倍） | 1 |
| `RETRY_MAX_ATTEMPTS_429` | 429の最大リトライ回数 | 3 |
| `RETRY_429_DEFAULT_WAIT_SECONDS` | `Retry-After`がない429の待機秒数 | 2 |
| `RETRY_MAX_WAIT_SECONDS` | 1回の待機の上限（`Retry-After`にも適用） | 30 |
| `CONNECT_TIMEOUT_SECONDS` | 接続タイムアウト | 5 |
| `RESPONSE_TIMEOUT_SECONDS` | 1試行の全体タイムアウト | 10 |

リトライ回数0は、リトライなしで1回だけ試行することを意味する。
最大リトライ回数Nは初回試行に加えてN回再試行する意味で、総試行回数は最大N+1回とする。
500/503と429が混在する場合は、各カウンターが独立なので、総試行回数は最大で`N_5xx + N_429 + 1`回になる。

設定値の規則は次のとおり。

| 規則 | 内容 |
| --- | --- |
| 値の形式 | 10進の非負整数のみ（正規表現`^[0-9]+$`、6桁以内）。負数、数値以外、小数、7桁以上は不正 |
| 空文字 | 未設定と同じ扱いで既定値を使う |
| 0を許す変数 | 2つのリトライ回数、`RETRY_BACKOFF_BASE_SECONDS`、`RETRY_429_DEFAULT_WAIT_SECONDS`、`RETRY_MAX_WAIT_SECONDS` |
| 1以上を要する変数 | `CONNECT_TIMEOUT_SECONDS`、`RESPONSE_TIMEOUT_SECONDS`（curlでは0が無制限になるため） |
| 5xxの待機 | `min(base * 2^(n-1), RETRY_MAX_WAIT_SECONDS)`。nは1始まりのリトライ番号 |
| 回数カウンター | 500/503と429で独立。混在しても各カウンターが上限に達した時点で終了する |
| タイムアウト整合 | `CONNECT_TIMEOUT_SECONDS`が`RESPONSE_TIMEOUT_SECONDS`より大きくても設定不備にしない |

不正な値は設定不備として、`CLIENT_ERROR=invalid_config`と終了コード78で停止する。

## 5. 非機能要件

| ID | 要件 |
| --- | --- |
| NFR-601 | M04の出力契約（`CLIENT_STATUS`、`CLIENT_BODY`、`CLIENT_ERROR`、終了コード78）を維持する |
| NFR-602 | プロキシ未設定時に直接通信しない動作を維持する |
| NFR-603 | M01〜M03のCompose、Squid、WireMock契約を変更しない |
| NFR-604 | 診断ログは標準エラーへ出力し、標準出力は`CLIENT_STATUS`と`CLIENT_BODY`の2行のみとする |
| NFR-605 | リトライの待機時間計算と対象判定を、実通信なしで検証できる。関数の単体検査とスタブ`curl`/`sleep`によるentrypoint検査は、`tests/m06-client-resilience.sh`の`unit`モードで行う。Composeスモークは同ファイルの`smoke`モードで行う（clarify決定、analyzeで1ファイルに統一）。本番スクリプトにテスト専用の分岐を持ち込まず、POSIX shで書く |

## 6. 対象外

- 複数宛先へのフェイルオーバーを行う本番用クライアント
- `Retry-After`のHTTP日付形式
- 503の`Retry-After`の尊重（`Retry-After`は429のみで参照する）
- タイムアウトのリトライ
- 500、503、429以外のステータスに対するリトライ
- サーキットブレーカー、ジッター、並列リクエスト
- WireMockシナリオによるリトライ成功の再現（M03マッピングの変更を要するため別途）
- Squid、WireMock、Composeの設定変更

## 7. 完了条件

- [ ] 500/503が設定回数まで指数バックオフで再試行され、上限到達後に最後のステータスが出力され、終了コードは0である
- [ ] 429で`Retry-After`の秒数が待機に使われ、ない場合は既定待機時間が使われる
- [ ] `Retry-After`が`RETRY_MAX_WAIT_SECONDS`を超えた場合は上限まで切り詰めて待機する（clarify決定・要確認）
- [ ] 500/503と429で、回数と待機ポリシーが別々に設定できる
- [ ] 接続タイムアウトとレスポンスタイムアウトが動作し、`CLIENT_ERROR=timeout`、終了コード28で終了する（遅延応答`/api/slow-5000`で実通信も確認する）
- [ ] 全設定が環境変数で変更でき、不正値は`CLIENT_ERROR=invalid_config`、終了コード78で停止する
- [ ] 診断ログに試行番号、待機時間、最終結果が含まれる
- [ ] 200などの成功応答とリトライ対象外ステータスで、再試行と待機が発生しない
- [ ] リトライ回数0と1、待機上限、`Retry-After`の0秒と上限超過、
  7桁以上（上限へ切り詰め）、空文字・形式不正（既定待機）の`Retry-After`の境界値が単体レベルで検証されている
- [ ] `retry-lib.sh`の存在確認がComposeスモークテストに含まれる
- [ ] M04の既存検証が引き続き通る（`/api/error-500`は`RETRY_BACKOFF_BASE_SECONDS=0`で実行する、clarify決定・要確認）
- [ ] M06のSpec Kit成果物と検証手順が保存されている
