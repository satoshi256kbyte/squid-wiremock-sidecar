# M06 clarify

## 前提

- M04の出力契約は`CLIENT_STATUS`、`CLIENT_BODY`、`CLIENT_ERROR`、プロキシ未設定時の終了コード78である。
- M04の`test-client/entrypoint.sh`は、curl失敗時に`CLIENT_ERROR=curl_exit_<rc>`を出力して`rc`で終了する。
- M04のHTTPエラーは通信成功として扱い、ステータスと本文を出力して終了コード0で終わる。
- `tests/m04-test-client.sh`は`/api/error-500`で`CLIENT_STATUS=500`と`Internal Server Error`だけを検査する。
- 「最大リトライ回数N」は初回試行に加えてN回再試行することを指し、総試行回数は最大N+1回とする。

## 論点と決定

### 1. 環境変数名と既定値

| 項目 | 内容 |
| --- | --- |
| 選択肢A | spec.md 4章の案をそのまま確定する |
| 選択肢B | 名称を統一プレフィックス（例`CLIENT_`）に変える |
| 選択肢C | 既定のリトライ回数を0にしてM04と同一動作にする |
| 決定 | 選択肢A。名称・既定値はspec.mdの案どおり |
| 理由 | 名称変更は利点が小さく、spec.mdとレビュー済みの記述を変えるリスクだけが残る |

既定値で追加で確定する規則は次のとおり。

| 規則 | 決定 |
| --- | --- |
| 値の形式 | 10進の非負整数のみ（正規表現`^[0-9]+$`、6桁以内） |
| 空文字 | 未設定と同じ扱いで既定値を使う（M04のテストが`-e VAR=`で未設定を表すため） |
| 0を許す変数 | 2つのリトライ回数、`RETRY_BACKOFF_BASE_SECONDS`、`RETRY_429_DEFAULT_WAIT_SECONDS`、`RETRY_MAX_WAIT_SECONDS` |
| 1以上を要する変数 | `CONNECT_TIMEOUT_SECONDS`、`RESPONSE_TIMEOUT_SECONDS`（curlでは0が無制限になるため） |
| 5xxの待機 | `min(base * 2^(n-1), RETRY_MAX_WAIT_SECONDS)`。nは1始まりのリトライ番号 |
| 回数カウンター | 500/503と429で独立。混在した場合も各カウンターが上限に達した時点で終了する |
| タイムアウト整合 | `CONNECT_TIMEOUT_SECONDS`が`RESPONSE_TIMEOUT_SECONDS`より大きい場合は設定不備にしない（curlが先に全体で打ち切る） |

spec.mdへの影響は次のとおり。

| 変更 | 更新箇所 |
| --- | --- |
| あり | 4章「設定」の末尾に、値の形式、空文字の扱い、0を許す変数、5xx待機式、カウンター独立を追記する |
| あり | 4章の見出し直下「名称と既定値の案は次のとおり。確定はclarifyで行う。」を確定表現に直す |

### 2. M04の`/api/error-500`スモークテストとリトライ

| 項目 | 内容 |
| --- | --- |
| 選択肢A | 既定のまま（5xx 3回、基準1秒）で実行する。待機は1+2+4=7秒かかる |
| 選択肢B | M04スモークテストに`-e RETRY_MAX_ATTEMPTS_5XX=0`を足し、リトライなしで検査する |
| 選択肢C | M04スモークテストに`-e RETRY_BACKOFF_BASE_SECONDS=0`を足し、リトライは行うが待機を0にする |
| 決定 | 選択肢C。既存の検査行は変えず、`/api/error-500`の`docker-compose run`にこの環境変数だけを足す |
| 理由 | 既定のリトライ経路を通したまま数秒の遅延を除ける。`/api/error-500`は常に500を返すので結果も決定的になる |

補足は次のとおり。

- 選択肢Aは変更不要だが、約7秒の遅延が増え、CIの待機時間のばらつきで不安定になりうる。
- 選択肢Bはリトライ経路が通らず、M06の退行を検知できなくなる。
- 診断ログは標準エラーなので、`$(...)`で標準出力だけを取るM04の検査行（`CLIENT_STATUS=500`）には影響しない。
- M06専用のスモークは`tests/m06-client-resilience.sh`の`smoke`モードとし、M04のテストとは分ける。待機を小さい値（0または1）に固定する。
- 変更するのは`error_output=$(docker-compose run ...)`の1コマンドだけで、M04の他の検査は変えない。

spec.mdへの影響は次のとおり。

| 変更 | 更新箇所 |
| --- | --- |
| あり | 2章「対象範囲」に「M04スモークテストの`/api/error-500`実行への待機0指定の追加」を追加する |
| あり | 7章「完了条件」の「M04の既存検証が引き続き通る」に「（`/api/error-500`は`RETRY_BACKOFF_BASE_SECONDS=0`で実行する）」を追記する |

### 3. タイムアウト時の終端結果

| 項目 | 内容 |
| --- | --- |
| 選択肢A | M04のまま`CLIENT_ERROR=curl_exit_28`、終了コード28 |
| 選択肢B | `CLIENT_ERROR=timeout`、終了コード28。curlの終了コードは診断ログに出す |
| 選択肢C | `CLIENT_ERROR=timeout`、M06専用の新しい終了コード（例124） |
| 決定 | 選択肢B |
| 理由 | 識別子を固定でき（FR-606の「固定の終端結果」）、終了コード28はM04でタイムアウト時に得られた値と同じで互換になる |

細則は次のとおり。

- 対象のcurl終了コードは28のみとする。接続拒否（7）などは従来どおり`curl_exit_<rc>`で終了コード`rc`とする。
- curlの終了コードは診断ログの最終結果行に`curl_exit=28`として残す（表面化はログのみで、`CLIENT_ERROR`は`timeout`に固定）。
- 接続タイムアウトとレスポンスタイムアウトは`--connect-timeout`と`--max-time`で設定する。両者とも終了コード28になるため出力は区別しない。
- タイムアウトはリトライ対象外とする（spec.md 6章の「500、503、429以外」に該当）。1回で終端する。
- `CLIENT_ERROR`は標準エラーへ出力し、標準出力は空にする（M04の通信失敗と同じ）。

spec.mdへの影響は次のとおり。

| 変更 | 更新箇所 |
| --- | --- |
| あり | FR-606を「タイムアウト（curl終了コード28）で試行が失敗した場合、標準エラーへ`CLIENT_ERROR=timeout`を出力し、終了コード28で終了する。リトライはしない」に具体化する |
| あり | FR-609の最終結果の値を`success`、`retries_exhausted`、`timeout`の3種に固定する旨を追記する |

### 4. 不正な設定値の終了コード

| 項目 | 内容 |
| --- | --- |
| 選択肢A | 78（M04の設定不備と同じ） |
| 選択肢B | 64（EX_USAGE） |
| 選択肢C | 2など独自の値 |
| 決定 | 選択肢A。標準エラーへ`CLIENT_ERROR=invalid_config`を出力し、終了コード78 |
| 理由 | M04で「設定不備」を78と定義済みで、利用側の判定を増やさない。M06のspec.mdも「設定不備」と表現している |

細則は次のとおり。

- どの変数が不正かは別行`CLIENT_DIAG invalid_config name=<変数名>`として標準エラーに出す（値そのものは出さない）。
- 検査順は、プロキシ未設定の検査（78、`proxy_not_configured`）を先、設定値の検査を後とする。両方不正なときは`proxy_not_configured`が優先される。
- 設定値の検査は最初の通信より前に完了し、不正時は通信しない。

spec.mdへの影響は次のとおり。

| 変更 | 更新箇所 |
| --- | --- |
| あり | 4章末尾の「固定の非ゼロ終了コード」を「`CLIENT_ERROR=invalid_config`と終了コード78」に具体化する |
| あり | FR-607に不正値の扱い（FR-607の追記または新規FR-612）を追加する |

### 5. リトライ上限到達後の終了コード

| 項目 | 内容 |
| --- | --- |
| 選択肢A | 最後のレスポンスを出力し、終了コード0（M04のHTTPエラー動作を維持） |
| 選択肢B | 最後のレスポンスを出力し、非ゼロ終了（例22） |
| 決定 | 選択肢A。5xxでも429でも上限到達時は`CLIENT_STATUS`と`CLIENT_BODY`を出力して終了コード0 |
| 理由 | NFR-601とM04の「HTTPエラーは通信成功」の契約を守れる。呼び出し側はステータスで判定できる。FR-611の記述とも一致する |

細則は次のとおり。

- リトライ上限到達は診断ログの最終結果`retries_exhausted`で識別する（終了コードでは区別しない）。
- 非ゼロ終了になるのは、タイムアウト、curl失敗、プロキシ未設定、設定不備のみとする。
- リトライ回数0で500が返った場合も、1回だけ試行して終了コード0とし、最終結果は`retries_exhausted`とする。
  リトライ対象ステータス（500、503、429）で終了した場合の最終結果は常に`retries_exhausted`である。

spec.mdへの影響は次のとおり。

| 変更 | 更新箇所 |
| --- | --- |
| あり | FR-611に「終了コードは0とする（M04のHTTPエラー動作を維持）」を追記する |
| あり | 7章の1項目目に「終了コード0」を加える |

### 6. `Retry-After`が上限を超えた場合

| 項目 | 内容 |
| --- | --- |
| 選択肢A | `RETRY_MAX_WAIT_SECONDS`で切り詰めて待機し、リトライを続ける |
| 選択肢B | 待機せず即時に終端する（`retries_exhausted`扱い） |
| 決定 | 選択肢A |
| 理由 | spec.mdの設定表が「`Retry-After`にも適用」と定めており、上限を安全弁として扱える。待機時間の最大値が設定で決まり、テストが決定的になる |

細則は次のとおり。

- 診断ログに、サーバー指定値と実際の待機時間の両方を出す（例`retry_after=120 wait=30 capped=1`）。
- `Retry-After: 0`は待機0秒で再試行する。リトライ回数のカウントは通常どおり消費する。
- 秒数形式（`^[0-9]+$`）以外（HTTP日付、負数、空、小数）は存在しないものとして扱い、429既定待機時間を使う。
- ヘッダー名は大文字小文字を区別せず、行末のCRを除去して解析する。同名ヘッダーが複数あれば最後の値を使う。
- `Retry-After`は429のみで参照する。503の`Retry-After`は今回は無視する（対象外に明記）。

spec.mdへの影響は次のとおり。

| 変更 | 更新箇所 |
| --- | --- |
| あり | FR-603に「上限超過時は`RETRY_MAX_WAIT_SECONDS`へ切り詰める。形式不正は存在しないものとして扱う」を追記する |
| あり | 6章「対象外」に「503の`Retry-After`の尊重」を追加する |

### 7. 429の待機方式

| 項目 | 内容 |
| --- | --- |
| 選択肢A | `Retry-After`がなければ固定待機（`RETRY_429_DEFAULT_WAIT_SECONDS`） |
| 選択肢B | `Retry-After`がなければ指数バックオフ |
| 決定 | 選択肢A（固定） |
| 理由 | FR-604が「既定待機時間」と定めている。FR-602の「500/503とは別の待機ポリシー」を満たし、設定が1つで済み計算の検証も単純になる |

固定待機にも`RETRY_MAX_WAIT_SECONDS`の上限を適用する。

spec.mdへの影響は次のとおり。

| 変更 | 更新箇所 |
| --- | --- |
| あり（明確化のみ） | FR-604に「固定待機で、指数的には増やさない。上限`RETRY_MAX_WAIT_SECONDS`を適用する」を追記する |

### 8. 待機計算とリトライ対象判定の単体レベル検証

| 項目 | 内容 |
| --- | --- |
| 選択肢A | 判定と計算を関数にして別ファイルに切り出し、ホストのシェルから読み込んで検査する |
| 選択肢B | スタブの`curl`と`sleep`をPATH先頭に置き、`entrypoint.sh`全体を実通信なしで実行する |
| 選択肢C | WireMockのシナリオでComposeを起動して検査する |
| 決定 | AとBの併用。純粋関数はA、ループと出力契約はBで検査する。Cは今回行わない |
| 理由 | 実通信なし（NFR-605）で境界値を網羅でき、Dockerを使わず速い。Cは時間がかかり、WireMockの状態変更（M03契約）にも触れる |

構成は次のとおり。

| ファイル | 役割 |
| --- | --- |
| `test-client/retry-lib.sh` | POSIX shの関数のみ（副作用なし）。`is_retryable_status`、`backoff_wait_5xx`、`resolve_429_wait`、`parse_retry_after`、`validate_config`を持つ |
| `test-client/entrypoint.sh` | `retry-lib.sh`を読み込み、ループ・curl呼び出し・出力を担当する |
| `tests/m06-client-resilience.sh` | `unit`で関数の単体検査とスタブのentrypoint検査、`smoke`でComposeスモーク。実通信は`smoke`だけ |

検査する境界値は次のとおり。

| 対象 | ケース |
| --- | --- |
| 対象判定 | 200、301、404は対象外。500、503、429は対象。501、502、504は対象外 |
| 5xx待機 | base=1でn=1,2,3が1,2,4。上限30で打ち切り。base=0は常に0 |
| 回数 | 5xx回数0（1回だけ試行）、1（最大2回）。429回数0、1も同様 |
| `Retry-After` | 0、5、上限ちょうど、上限+1（切り詰め）、HTTP日付・負数・空（既定待機）、ヘッダー名の大文字小文字 |
| 設定検証 | 負数、非数値、小数、7桁以上は`invalid_config`。空文字は既定値。タイムアウト0は不正 |
| 出力契約 | 診断ログが標準エラーのみ。標準出力は`CLIENT_STATUS`と`CLIENT_BODY`の2行のみ |
| 終端 | タイムアウト（スタブがrc=28）で`CLIENT_ERROR=timeout`、終了コード28、リトライなし |

実装上の取り決めは次のとおりである。

- 待機は`sleep`コマンドを呼ぶだけとし、テスト専用の環境変数や分岐は本番スクリプトに持ち込まない（PATHのスタブで代替）。
- `retry-lib.sh`はテスト・本番とも同じ実体を読み込む。DockerfileでのCOPY漏れを防ぐため、Composeスモークテストに`retry-lib.sh`の存在確認を含める。
- ホストのシェルで動かすため、bash固有の機能（配列、`[[ ]]`）は使わず、M04と同じPOSIX shで書く。

spec.mdへの影響は次のとおり。

| 変更 | 更新箇所 |
| --- | --- |
| あり | 2章「対象範囲」に「リトライ判定・待機計算の関数分離（`test-client/retry-lib.sh`）」を追加する |
| あり | NFR-605に「関数の単体検査とスタブ`curl`/`sleep`によるentrypoint検査で行う」を追記する |
| あり | 7章の境界値の項目に「7桁以上・空文字・形式不正な`Retry-After`」を加える |

## ユーザー確認が必要な判断

人が確認すべき、製品または互換性に影響する判断のみを挙げる。他の論点は推奨どおり進める。

| 判断 | 影響 | 推奨既定 |
| --- | --- | --- |
| リトライを既定で有効にする（5xx 3回、429 3回） | 既存利用者の`/api/error-500`が約7秒遅くなる。WireMockの呼び出し回数がM04の1回から4回に増える | 有効（spec.mdの案どおり）。M04スモークは待機0で実行 |
| タイムアウトの`CLIENT_ERROR`を`timeout`に変える | M04では`curl_exit_28`だった識別子が変わる。終了コードは28のまま | `CLIENT_ERROR=timeout`、終了コード28 |
| リトライ上限到達後も終了コード0にする | 呼び出し側が`CLIENT_STATUS`を見ないと失敗を見逃す | 終了コード0（M04の契約維持） |
| M04スモークテストの`/api/error-500`に`-e RETRY_BACKOFF_BASE_SECONDS=0`を足す | M04側のテストファイルを1行変更する | 足す（検査行は変更しない） |
| `Retry-After`が上限を超えたら上限まで切り詰めて待つ | 呼び出し側の最大待機時間が`RETRY_MAX_WAIT_SECONDS`で決まる | 切り詰める（即時失敗にはしない） |

## 対象外（再確認）

- 503の`Retry-After`の尊重
- HTTP日付形式の`Retry-After`
- タイムアウトのリトライ
- ジッター、サーキットブレーカー、並列リクエスト
- WireMockシナリオによるリトライ成功の再現（M03マッピングの変更を要するため別途）
- Squid、WireMock、Composeの設定変更
