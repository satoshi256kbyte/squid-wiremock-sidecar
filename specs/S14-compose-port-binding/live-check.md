# S14 実機確認の記録（T1401）

## 環境

| 項目 | 内容 |
| --- | --- |
| ホストOS | macOS（Apple Silicon、aarch64） |
| コンテナランタイム | Colima（macOS Virtualization.Framework、runtime は docker、マウントは virtiofs） |
| Compose | docker-compose 5.6.1。`docker compose` ではなく `docker-compose` を使用した |
| イメージ | ubuntu/squid:latest、wiremock/wiremock:3.13.1 |
| 実験の場所 | 8.1、8.3、8.4 と 8.5 の手順3は、作業用ディレクトリ配下の使い捨てコピー（T1402とT1403の変更を適用） |
| 実験の場所（8.5） | 8.5 の手順1と2は、リポジトリ直下の `.s14-deny.<PID>` を使った |
| Linux環境 | なし。8.2 の手順を実行できる Linux のホストまたは CI ランナーを、この作業では用意できなかった |

## 手順

1. 事前確認を行った。Q-002 は `clarify.md` の承認記録（2026-11-03）で確認した。Colima は稼働中で、
   Compose のコンテナは 0 件、ポート 3128 と 8080 は使用されていなかった。
2. 使い捨てコピーを作り、Squid の送信元ACL（`local_src`）と、ホスト公開のループバック固定を入れた。
   プロジェクト名は `s14t1401copy` を明示した。
3. 隔離の確認を行った。コンテナ内の `squid.conf` に送信元ACLが見えること、ホストとコンテナの
   WireMock 用ファイル数が一致すること、WireMock の管理APIでマッピングが読めることを確かめた。
4. 8.4 の `docker-compose config --format json` を、デーモンへ接続できる場合と、接続できない場合の両方で実行した。
5. 8.1 を行った。許可ドメインのマッピングを投入し、ホストからSquid経由で要求した。
   続けて許可外ドメインを要求した。最後に、テストクライアントの one-shot 実行（`CLIENT_STATUS` を出力する）の結果を確かめた。
6. 8.3 を行った。現行の `squid.conf`（git の HEAD）と変更後の設定で `squid -k parse` を実行した。
   未定義のディレクティブを足した写しでも実行した。
7. 8.5 の手順1と2を行った。リポジトリ直下に `.s14-deny.<PID>` を作り、`squid.conf` の写しと上書き用の Compose ファイルを置いた。
   上書きファイルで `ports` を空にし、本番の設定の全インターフェース公開を一時的にも作らないようにした。
   squid だけを起動し、コンテナ内の設定がホストの写しとバイト単位で一致することを確かめた。
8. 8.5 の手順3を行った。`mktemp -d` が作る一時ディレクトリに同じ写しを置き、同じ方法で起動を試した。
   対照として、リポジトリ直下のディレクトリを、一時コンテナへの読み取り専用マウントで見た。
9. 後始末を行った。各プロジェクトを `down --remove-orphans` で止め、写しと上書きファイルを削除した。

## 観測

| 確認項目 | 結果 | 観測 |
| --- | --- | --- |
| 8.1 許可ドメイン（ホストからSquid経由） | 成功 | HTTP 200。本文を確認した。アクセスログの判定は `TCP_MISS/200` |
| 8.1 許可外ドメイン | 拒否 | HTTP 403。アクセスログの判定は `TCP_DENIED/403` |
| 8.1 Test Client 経由 | 成功 | テストクライアントの終了コードは 0。`CLIENT_STATUS=200`。アクセスログは `TCP_MISS/200` |
| 8.1 送信元の範囲 | 範囲内 | ホストとテストクライアントの送信元は、どちらも RFC1918 の 3 範囲のいずれかに入った（アドレスは記録しない） |
| 8.3 現行設定の parse | 終了コード 0 | WARNING 3 件。ERROR と FATAL はなし |
| 8.3 変更後設定の parse | 終了コード 0 | WARNING 3 件（現行と同数）。ERROR と FATAL はなし。`local_src` による新しい WARNING はなし |
| 8.3 未定義ディレクティブの parse | 終了コード 1 | 出力は `unrecognized: '<ディレクティブ名>'` を含む 1 行。`ERROR` と `FATAL` の文字列はなし |
| 8.4 `config --format json` | 成功 | デーモン接続の有無に関係なく、終了コード 0。squid と wiremock の `ports` に `target`、`published`、`host_ip`、`mode`、`protocol` がある。`host_ip` はループバックアドレス |
| 8.5 手順1（マウントと起動） | 成功 | `up` の終了コード 0。squid は running |
| 8.5 手順2（コンテナから見えるか） | 成功 | コンテナ内の設定とホストの写しがバイト単位で一致した（`cmp`） |
| 8.5 手順3（一時ディレクトリ） | 見えない | `mktemp -d` のディレクトリはマウントできず、起動が `not a directory` で失敗した |
| 8.5 対照（リポジトリ直下） | 見える | 同じ方法で、リポジトリ直下のディレクトリのファイルが一時コンテナから見えた |
| 8.2 Linux CI の送信元 | 未確認 | Linux のホストまたは CI ランナーがないため、実行していない |
| 後始末 | 完了 | 使い捨てコピーと本番の確認のプロジェクトは `down --remove-orphans` で止めた。写しと上書きファイルは削除した |

テストクライアントは one-shot で、要求を1回送ると終了する。そのため、`docker-compose exec -T test-client` は
`service "test-client" is not running` で失敗した。T1405 の順7は、`docker-compose run` などの one-shot の実行方法に直す必要がある。

8.3 の未定義ディレクティブは、`ERROR` や `FATAL` を出さない。そのため、T1405 の順8を
`ERROR` と `FATAL` の文字列だけで判定すると、この失敗を見逃す。判定には終了コードの非0も使う。

8.5 手順3の一時ディレクトリは、コンテナのマウントに使えなかった。T1405 の範囲外の検査はリポジトリ直下に置く設計のままでよい。
将来の利用者向けの注意として、macOS の `mktemp -d` の場所（`/var/folders` 配下）は Colima の VM から見えないと残す。

## 結論

- 8.1 は成功した。許可ドメインは送信元ACLを通り、許可外は拒否された。Test Client 経由の要求も成功した。
- 8.3 は判定を一部直す必要がある。WARNING だけの設定は終了コード 0 で、未定義のディレクティブは終了コード 1 だった。
  終了コードと文字列の両方で判定する。
- 8.4 は成功した。`published`、`target`、`host_ip` がそろって得られ、`plan.md` 4.3 の方式で `static` を書ける。
- 8.5 手順1と2は成功した。リポジトリ直下に置いた写しは squid から見えるため、`plan.md` 4.3 の設計をそのまま使う。
  手順3は見えなかった。見えない場合の方式（`docker-compose cp`）への変更は、手順1と2が失敗したときの規定であり、今回は当てはまらない。
- 8.2 は未確認である。残リスクとして R-02 を `security-review.md` に書き、M09 の CI 導入時の確認項目へ引き継ぐ。
- 失敗した確認項目はない。T1402 以降の着手を妨げる結果はない。
- T1405 は、one-shot の Test Client の扱いと、8.3 の終了コードの判定を反映して実装する。

## T1405 の実行結果

`sh tests/s14-compose-port-binding.sh live` を実行した結果を記録する。アドレスは記録しない。

| 項目 | 結果 |
| --- | --- |
| 連続実行 | 3回連続で成功した。毎回 12 PASS、終了コード 0 |
| 後始末 | 実行後にコンテナが残らず、`.s14-deny` のコピーも残らなかった |
| 最初の実行 | 1回だけ失敗した |

最初の live 実行が失敗した原因は、再現しなかった。
Squid から WireMock への経路の準備待ちを足した後は、失敗が出ていない。
この待機は、厳密な確認の前に、上流の応答本文を確かめてから進む。

範囲外の送信元の拒否は、Compose ネットワークの内側から、one-shot の Test Client で確認した。
上書きファイルがホスト側のポートを空にするため、ホストからは確認できない。
この点が、仕様のホスト側からの確認という書き方と異なる。
