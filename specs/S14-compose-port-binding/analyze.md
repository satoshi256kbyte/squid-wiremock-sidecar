### A-01 中断時の後始末（High）

tasks 1.4の規則6は、「正常終了、失敗終了、中断のどれでも消える」ことを求める。
plan 4.3（150行）とtasks T1405（210行）は、`trap cleanup EXIT`だけを置く。

`EXIT`の`trap`は、`TERM`で終了されたとき、macOSの`sh`とbashでは動いた。
`dash`では動かない。Linuxの多くの`/bin/sh`は`dash`であり、M09のCIでは、中断された実行が
`.s14-deny.<PID>`とコンテナを残す。`.gitignore`は変えない規則（規則4）のため、消し残しは
`git add .`やエディタ上の操作で取り込まれうる。

M03の検査も`EXIT`だけである。ただしM03は、リポジトリ内に一時ファイルを作らない。
S14はリポジトリ直下に作るため、同じ作りでは足りない。

修正案は次のとおり。

| 項目 | 内容 |
| --- | --- |
| plan 4.3の後始末 | `trap cleanup EXIT`に加え、`trap 'exit 130' INT`と`trap 'exit 143' TERM`を置く。シグナルで`exit`し、`EXIT`の`trap`を必ず通す |
| T1405の検査 | `live`の実行中に`TERM`を送り、`docker-compose ps -aq`が空で、`.s14-deny.`が残らないことを確かめる |
| 不可能な場合 | `SIGKILL`は捕捉できない。その場合の手動の回収をtasks 1.4の規則7に残す |

### A-02 `git status`の検査が通り続ける（High）

tasks 1.4の規則7、T1405（208、224行）、T1411（342行）、完了条件（388行）は、
`git status --short`に「`.s14-deny.`で始まる行がない」ことを確かめる。
実測では、直下の使い捨てディレクトリは`?? .s14-deny.<PID>/`と表示される。行頭は「??」と空白である。

実装者が`grep '^\.s14-deny\.'`のように書くと、消し残しがあっても何も一致せず、検査は常に通る。
未追跡のディレクトリは、`git status --short`で1行にまとめて表示されるため、中身の確認にも向かない。

修正案は次のとおり。

| 項目 | 内容 |
| --- | --- |
| 判定の書き方 | `git status --short \| grep -F '.s14-deny.'`が何も出力しないこと（`grep`の終了コードが1）と書く |
| 補強 | `ls -d .s14-deny.* 2>/dev/null`が空であることも併せて確かめる |
| 失敗を確かめる | 検査の動作確認で、わざと`.s14-deny.test`を作り、検出されることを確かめてから消す |

T1401（126行）の「`git status --short`が実験の前後で同じ」も、`specs/S14-compose-port-binding/`が
未追跡で1行にまとまるため、その配下の変化は見えない。T1401が見たいのは、ほかのファイルが変わっていないことなので、
`git status --short`に加えて`git diff --stat`が空であることを使う。

### A-05 壊した写しに対する`static`の実行方法（Medium）

plan 4.3（168から169行）とtasks T1404（197から198行）は、`mktemp -d`配下に壊した写しを作り、
写しの側で検査して失敗することを確かめるとする。一方で、本番のスクリプトに、テスト専用の分岐や環境変数は
入れない（plan 24から25行、tasks 76から77行）。

`static`が現在の作業ディレクトリの相対パスだけを読む作りなら、スクリプト自体を写しにも置き、
写しのディレクトリで実行すれば、分岐なしで検査できる。この前提がどこにも書かれていない。
`docker-compose config`も、作業ディレクトリのComposeファイルを読む。

T1404に、「スクリプトは作業ディレクトリの相対パスだけを使う」「確認では、スクリプトを写しへコピーして
写しのディレクトリで実行する」と書く。
