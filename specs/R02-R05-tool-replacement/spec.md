# R02〜R05 一般的なツールへの置き換え仕様（actionlint、gitleaks、bats-core、jq）

## 1. 背景と目的

AGENTS.mdの方針は、検査や補助の仕組みに一般的なツールがあればそれを使い、版を固定して導入することである。
自前のチェック用シェルや独自の検査は、一般的なツールで代えられない理由を示せる場合だけ作る。
R01（shellcheck）はこの方針の最初の適用である。
本Specは、残る4件を一つの仕様にまとめる。

| Roadmap ID | Issue | 置き換え先 | 置き換える対象 |
| --- | --- | --- | --- |
| R02 | #34 | actionlint、YAMLの構造比較（`yq`または`jq`） | `tests/m09-execution-and-ci.sh`の`t_wf_*`（grepと字下げの完全一致、PyYAMLの分岐） |
| R03 | #35 | gitleaksと`.gitleaks.toml` | 識別情報のgrep（`[0-9]{12}`、`arn:aws`、`AKIA`） |
| R04 | #36 | bats-core | `check`、`must`、`rc_is`、`expect`、偽のdockerとawsの用意、結果の集計の重複 |
| R05 | #37 | jq | `python3 -c`、grep、sedによるJSONの単純な値の取り出し |

前提は次のとおりとする。

| 項目 | 前提 |
| --- | --- |
| 方針 | 一般的なツールがあるときは自前の検査を作らない。導入するツールは版を固定する |
| 実行環境 | CI（ubuntu-24.04）、ローカルのmacOS（Colima利用）、ローカルのLinux |
| 判定の維持 | 置き換えの前後で、判定（成功と失敗の別）と終了コードを弱めない |
| 依存 | R04はR01に依存する。R05はR01〜R04に依存する。R02とR03は独立である |
| 手本 | R01（`specs/R01-shellcheck/spec.md`）の版の固定（`mise.toml`と`mise.lock`）と、品質ゲートでの実行の方式 |

### 2.2 R04の範囲の決め方

R04はIssueのとおり段階的に進める。
まず小さいファイルと新しいテストを移し、その結果（検査の数の一致、実行時間、書き換えの手間、信号と`exit`の扱い）を見て、大きいファイルを移すかを判断する。
`tests/m06`（595行）と`tests/m07`（690行）はIssueに明記がない。
中間の規模のため、判断の対象にclarifyで加えるかを決める。

今回の一括の中での扱いは、clarifyで決める。候補は次の2つである。

| 候補 | 内容 |
| --- | --- |
| (a) 今回は小さいファイルだけ | `tests/m02`〜`m05`、`tests/s14`と新しいテストを移す。大きいファイルは移行の結果を文書に残し、別のIssueで判断する。この案はIssueの段階の定めに沿い、変更量と回帰の危険を抑える |
| (b) 大きいファイルも含める | (a)に加えて`tests/m09`（約320関数）と`tests/m08`を移す。重複を最も減らせるが、変更量が大きく、判定が同じであることの確認が重い |

推奨は(a)である。理由は、Issueが「小さいファイルの結果を見て判断する」と定めており、結果を見る前に大きいファイルを含めると、その定めに反するためである。

## 5. 版の固定と導入

### 5.1 固定する版

導入時に固定する版は、2026-11-08に各リポジトリの最新の安定版を確かめた値である。
導入の作業の時点で最新を確かめ直し、より新しい安定版があればplanで更新する。

| ツール | 版 | 確かめた日付 | 公開日 | 確かめた方法 |
| --- | --- | --- | --- | --- |
| actionlint | v1.7.12 | 2026-11-08 | 2026-03-30 | `rhysd/actionlint`の最新リリース |
| gitleaks | v8.30.1 | 2026-11-08 | 2026-03-21 | `gitleaks/gitleaks`の最新リリース |
| bats-core | v1.14.0 | 2026-11-08 | 2026-07-21 | `bats-core/bats-core`の最新リリース |
| jq | jq-1.8.2（1.8.2） | 2026-11-08 | 2026-06-20 | `jqlang/jq`の最新リリース |

`yq`を選ぶ場合の版は、Q-R0202の決定後にplanで確かめて記録する。

### 5.2 導入方式の候補（Q-R0203）

| 候補 | 内容 | 利点 | 欠点 |
| --- | --- | --- | --- |
| A. 全てmiseで導入する（R01の方式を拡張） | `mise.toml`の`[tools]`に4つ（と`yq`）を足し、`mise.lock`にURLとSHA256を持つ。CIはR01の`jdx/mise-action`で`--locked`導入する | 版とSHA256が一か所で固定される。R01と同じ手順で、環境の差が出にくい | miseがツールの取得元（aqua、ubi、github）を解決するため、各ツールが4つの環境で`mise.lock`に載ることを確かめる必要がある。batsはシェルのスクリプトで、miseでの導入の形を確かめる必要がある |
| B. 個別に取得する | CIは公式のリリースの資産を、SHA256を照合して取得する。ローカルはOSの管理ツール（Homebrew、apt）で入れる | miseに載らないツールも扱える | 環境ごとに手順が分かれ、版とSHA256の宣言が分散する。取得用のシェルを自前で書く恐れがある（NFR-R0201に反する） |
| C. 一部だけmise、残りは個別 | miseで入るものはmise、入らないものだけ個別 | 影響を最小にできる | 方式が混在し、文書と検査が増える |

推奨はAである。理由は、R01で`mise.toml`と`mise.lock`の方式を確立済みで、版とSHA256を一か所で固定でき、自前の取得用シェルを作らずに済むためである。
miseで4つの環境の導入ができないツールがあれば、そのツールだけCを採り、理由を記録する。

### 5.3 環境ごとの確認

| 環境 | 確認 |
| --- | --- |
| CI（ubuntu-24.04） | 導入のstepが、固定した版を導入し、各ツールの`--version`が期待と一致する |
| ローカルのmacOS（Colima利用） | 導入手順を実行し、品質ゲートが通る。アーキテクチャはarm64を想定する |

## 6. 既存の判定を弱めないこと

| 項目 | 内容 |
| --- | --- |
| 終了コード | 成功は0、失敗は0以外。ツールの終了コードを品質ゲートへ反映し、`\|\| true`などで握りつぶさない |
| 契約 | `t_wf_*`が固定する契約、識別情報の不在、FR-918（マスクして残りを削除）、各テストの検査の数と判定を保つ |
| SKIP | ツールが無いことを理由にSKIPして成功に数えない。無いときは失敗とし、導入手順を示す |
| 比較の方法 | 置き換えの前後で、同じ入力に同じ判定になることを確かめる。成功する入力と、契約を壊した入力の両方で確かめる |
| 範囲 | 検査する範囲は、置き換えの前と同じ以上とする |
