# S26 既存E2E検査のタスク定義方式への移行仕様

## 1. 目的

M09で導入済みのECSタスク定義方式へ、M02〜M08とS14の検査を移行する。
検査の実行基盤を`scripts/e2e.sh`とpauseコンテナ方式に一本化し、docker-composeの併用と切り戻し経路を残さない。
移行の最後に`docker-compose.yml`と現行のCompose前提記述を削除する。

本SpecはIssue #26とIssue #27を統合したものである。Issue #27は本Specの最後のタスクとして扱い、
このブランチのPRで統合済みとしてクローズする。

前提は次のとおりとする。

| 項目 | 前提 |
| --- | --- |
| 新基盤 | M09で導入済み。入口は`scripts/e2e.sh`のstart、test、stop、clean、logs、test:ci、collect |
| 起動方式 | タスク定義から変換した`docker run`、pauseコンテナによるネットワーク名前空間共有 |
| 管理対象 | 接頭辞`swsc-`とラベル`swsc.managed=true`で特定する |
| 廃止方式 | `docker-compose.yml`を削除し、Composeを呼ぶ経路を残さない |
| 既存契約 | Clientの出力、終了コード、WireMockのシナリオ期待値を維持する |
| 維持事項 | #23の`wiremock_verify_reset`内部要求除外を維持する。M08のTERM失敗再発を移行後smokeで確認する |

## 2. 対象範囲

対象は、既存検査の実行経路、品質ゲート、CI、現行文書である。過去のSpec Kit成果物は変更しない。

| 検査 | 現在確認できるCompose依存 | 移行後に満たす契約 |
| --- | --- | --- |
| M02 | `squid`への`docker-compose exec`、WireMockの8080、Squidの3128、サービス名依存 | `e2e.sh`で起動済みのWireMockとSquidを使い、Squidログを新基盤の収集経路で確認する |
| M03 | `up`と`down`、WireMockの8080、シナリオのマウント、Composeの起動待ち | WireMockシナリオを新基盤へ渡し、同じシナリオ検証と後処理を行う |
| M04 | `squid`と`wiremock`のサービス指定、`test-client`のone-shot実行、8080と3128 | Clientを検証ごとに実行し、同じ出力と終了コードを確認する |
| M05 | `squid`と`wiremock`の閉域ネットワーク、Clientのone-shot、Squidログ取得、`down` | pause方式のlocalhost共有とWireMock宛先で閉域通信を再現する |
| M06 | Compose起動、Clientのone-shot、終了コード28、ログ取得、`down`と残存確認 | リトライ、タイムアウト、cleanupの契約を新基盤のClient実行で維持する |
| M07 | WireMockの8080、Squidの3128、シナリオリセット、`down`、Compose残存確認 | シナリオを検査ごとに隔離し、管理対象だけを停止・削除する |
| M08 | `m08-e2e`プロジェクト名、8080と3128、Clientのone-shot、`down`、4シナリオ | 正常、500後に成功、429、タイムアウトをCIでも実行する |
| S14 | `sidecar`ネットワーク、Composeの`config`、プロジェクト名、公開ポート、設定マウント | 派生元設定の固定行と、移行後に使う派生設定の公開範囲を検査する |

Compose定義では、サービス名は`test-client`、`squid`、`wiremock`、ネットワーク名は`sidecar`である。
Squidの設定と許可リスト、WireMockシナリオをホストから読み取り専用でマウントし、8080と3128を公開する。
M09のMiniStack契約検証で使う4566は、現行Composeの依存ではない。

## 4. 契約

入口は、M09で定めた`scripts/e2e.sh`と`npm run`の契約を使う。startはWireMock、pause、Squidを起動し、
testはClientを検査ごとに実行する。test:ciは検査、収集、停止を順序づけ、失敗時もcleanupを行う。
stopとcleanはラベルと接頭辞で対象を限定する。logsとcollectは、停止前にSquid、WireMock、Clientの
調査に必要な出力を収集できるようにする。

移行対象の検査は、次の契約を保つ。

| 契約 | 内容 |
| --- | --- |
| 通信 | ClientからSquidへlocalhostで接続し、SquidからWireMockへ閉域で接続する |
| Client | Clientの標準出力、診断出力、HTTPステータス、終了コードを変更しない |
| シナリオ | WireMockのマッピングとリセットを検査間で隔離する |
| 後処理 | 成功、失敗、INT、TERMのいずれでも管理対象を回収する |
| CI | ローカルと同じ入口を使い、M08の4シナリオを含む検査結果を保持する |
| 記録 | 実測したCI時間、タイムアウトの根拠、ポート排他方法、grep結果を文書に残す |

### 5.2 検証方法

| 検証 | 方法 |
| --- | --- |
| 期待値 | 各検査を新基盤で実行し、既存の出力、終了コード、シナリオ結果と比較する |
| 起動と隔離 | `scripts/e2e.sh`のunit、smokeを使い、ラベル、接頭辞、pause共有、ポート排他を確認する |
| S14 | 固定ACL行、派生設定のparse、loopback公開、拒否ログ、読み取り専用入力、ソケット不使用を移行後の検査で確認する |
| M08 | CIで4シナリオを実行し、各シナリオの期待値と実行時間を記録する |
| 品質ゲート | `scripts/quality-gate.sh`からCompose設定展開とCompose残存検査が消え、ラベル確認へ変わったことを確認する |
| Compose削除 | `docker-compose.yml`削除後に品質ゲートとCIを実行し、一回限りのgrepで呼び出し0件を記録する |
| 文書 | README、docs、AGENTS.mdの現行記述が入口、排他、CI範囲と一致することを確認する |
| 識別情報 | 生成物、ログ、アーティファクト、文書を検査し、アカウント識別子とARNがないことを確認する |

M09の初回CI実測は、unit、test-ci、smoke、contractの合計が約2分46秒だった。
S26ではM08の4シナリオを加えた実測で、既存の時間とタイムアウトを見直す。
