# M08 代表4シナリオのE2Eテストスイートの仕様

## 1. 目的

M05の閉域経路、M06のTest Clientのリトライとタイムアウト、M07のシナリオ選択とリセットを組み合わせ、
代表4シナリオ（正常、500後の成功、タイムアウト、429とバックオフ）を一つのスイートとして自動実行する。
各シナリオについて、期待するHTTPステータス、リトライ回数、終了結果を検証し、
失敗時には再現に必要なシナリオ名とログを出力する。

要件の出典はIssue #8とする。Issue #8の本文はclarifyで取得して比較済みで、矛盾はない（Q-801、clarify.md参照）。
FR-809、FR-811、NFR-805は、Issueに記載がなく、このspec.mdが追加した要件である。

## 2. 対象範囲

- 次の4シナリオの自動実行と結果検証（3章、5.1）
  - 正常系（200）
  - 500エラーとリトライ後の成功
  - 503または遅延によるタイムアウト
  - 429とバックオフ
- 各シナリオの検証項目: HTTPステータス、リトライ回数、終了結果
- シナリオごとのテストレポート（シナリオ名、期待値、実測値、合否）
- 失敗時の再現用シナリオ名と、Test Clientの診断ログ、必要なコンテナログの出力
- ローカルで一つのコマンドから、スイート全体を実行できること
- 実行前後のWireMock状態のリセット（M07の`wiremock_reset`と`wiremock_verify_reset`を使う）
- 失敗経路を含む、Composeのコンテナと一時データの回収
- `scripts/quality-gate.sh`の検査リストへの登録（M07の後ろ、`s14`の前。実装時に実測して判断する。8章）
- Spec Kit成果物と検証手順のリポジトリへの保存（`specs/M08-e2e-suite/`）

## 3. 機能要件

| ID | 要件 |
| --- | --- |
| FR-801 | 代表4シナリオを、利用者の手作業なしで順に自動実行する。シナリオの選択にはM07のシナリオ名を使う（FR-701）。 |
| FR-802 | 正常系シナリオ（`normal`、`/api/users/123`）で、`CLIENT_STATUS=200`、最終結果`success`、総試行1回、リトライ0回、WireMockの受信1回を検証する。 |
| FR-803 | 500後に成功するシナリオ（`error-500-then-200`、`/api/error-500-then-200`）で、`CLIENT_STATUS=200`、最終結果`success`、総試行2回、リトライ1回（500の再試行）、WireMockの受信2回を検証する。待機は既定の`RETRY_BACKOFF_BASE_SECONDS=1`のままとし、診断ログの`retry attempt=1 status=500 class=5xx retry=1/3 wait=1`を確かめる（Q-808）。 |
| FR-804 | タイムアウトのシナリオで、`CLIENT_ERROR=timeout`、終了コード28、標準出力が空であること、最終結果`timeout`、総試行1回、リトライ0回を検証する。遅延には`slow-5000`（`/api/slow-5000`、5000ms）を使い、`RESPONSE_TIMEOUT_SECONDS=1`に設定する（M06の`smoke`で実機確認済みの値）。WireMockの受信回数は1回を検証する。Q-810の実機確認で、クライアントが切断した後もジャーナルに即時記録され、待機は不要と分かった（`q810-experiment.md`）。503を使う構成は含めない（Q-802）。 |
| FR-805 | 429のシナリオ（`ratelimit-429`、`/api/ratelimit`）で、`CLIENT_STATUS=429`、最終結果`retries_exhausted`、総試行4回（`RETRY_MAX_ATTEMPTS_429`の既定3＋1）、リトライ3回（`RETRY_MAX_ATTEMPTS_429`）、各待機が`Retry-After: 2`に従うこと（診断ログの429の`retry`行3本が、それぞれ`retry_after=2 wait=2 capped=0`）、WireMockの受信回数が総試行と一致することを検証する。終了コードは0とする（M06のFR-611）。総試行4とリトライ3は固定値でスイートに書き、M06の既定値が変わったら失敗して契約の変更を検知できるようにする（Q-811）。 |
| FR-806 | 各シナリオの検証は、Test Clientの標準出力（`CLIENT_STATUS`、`CLIENT_BODY`）、標準エラーの診断ログ（`CLIENT_DIAG`）、終了コード、WireMockのリクエストジャーナルの4つから期待値を引く。Test Clientの契約は変えない。 |
| FR-807 | 各シナリオの開始前に、M07の`wiremock_reset`と`wiremock_verify_reset`で初期状態にする。確認に失敗したら、そのシナリオを実行せず`FAIL`（未実行）として記録し、残りのシナリオも実行せず`未実行`（レポートの`result`は`NOT_RUN`）と記録して、スイートを失敗（終了コード1）にする（Q-806）。 |
| FR-808 | 各シナリオは、他のシナリオの結果に依存しない。実行順を入れ替えても各シナリオの合否が変わらない。 |
| FR-809 | 実行後にテストレポートを標準出力へ表形式のテキストで出力し、ファイルは作らない（ファイル保存はM09、Q-803）。1シナリオにつき1行で、シナリオ名、期待値、実測値、合否（`PASS`または`FAIL`。リセット確認の失敗で実行しなかった後続のシナリオは`NOT_RUN`）を含む。期待値と実測値は`status=200 result=success attempts=1 retries=0 wiremock=1 rc=0`の形で同じ項目名を並べる。最後の行に、全体の合否、合格数と失敗数、失敗したシナリオ名の一覧、所要時間（秒）を出す。機械可読形式は作らない。 |
| FR-810 | シナリオが失敗したとき、再現用のシナリオ名、実行した条件（パスと上書きした環境変数の名前と値）、そのシナリオの診断ログを、標準エラーへ出力する。値に認証情報を含めない。 |
| FR-811 | アサーションが失敗しても、残りのシナリオは実行し、最後に全体の合否と失敗したシナリオの一覧を出す。リセット確認の失敗だけは例外で、残りを実行しない（FR-807）。終了コードは、すべて合格なら0、一つでも失敗なら1とする（Q-806）。 |
| FR-812 | ローカルで一つのコマンド`sh tests/m08-e2e-suite.sh [unit\|smoke] [シナリオ名...]`から、Composeの起動、4シナリオの実行、レポート出力、後始末までを行える。引数なしは`smoke`とする（Q-804、Q-814）。終了コードは、0が全件合格、1が一つでも失敗、2が引数の誤り（不正なモード、未知またはE2E対象外のシナリオ名、`unit`への名前の指定）である。`package.json`は変えない。M09が`pnpm test`で包む。 |
| FR-813 | 終了時（成功、アサーション失敗、`INT`、`TERM`）に、Composeのコンテナと一時ディレクトリを回収する。終了コードは元の結果を保つ（M07のFR-710と同じ方式）。 |
| FR-814 | 検証手順（実行方法、各シナリオの期待値、失敗時の見方、所要時間の目安）を、リポジトリの文書に残す。置き場所は`docs/E2Eテスト.md`とし、`README.md`の「Testing Scenarios」から参照する（Q-807）。 |

## 4. シナリオ契約

4シナリオの期待値を次に固定する。既定の設定値はM06の4章に従い、シナリオ側で上書きする変数だけを示す。

| シナリオ | 名前とパス | 上書きする設定 | 期待するステータス | 期待する結果 | 総試行 | リトライ回数 | WireMock受信 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 正常 | `normal`、`/api/users/123` | なし | 200 | `success`、終了コード0 | 1 | 0 | 1 |
| 500後に成功 | `error-500-then-200`、`/api/error-500-then-200` | なし | 200 | `success`、終了コード0 | 2 | 1 | 2 |
| タイムアウト | `slow-5000`、`/api/slow-5000` | `RESPONSE_TIMEOUT_SECONDS=1` | なし（`CLIENT_STATUS`は出力されない） | `timeout`、終了コード28 | 1 | 0 | 1 |
| 429とバックオフ | `ratelimit-429`、`/api/ratelimit` | なし | 429 | `retries_exhausted`、終了コード0 | 4 | 3 | 4 |

リトライ回数は総試行−1で、診断ログの`retry`行の数とも突き合わせる。

429のシナリオは、WireMockが常に429を返すため、成功には至らず`retries_exhausted`で終わる。
M07のspec.mdは「429の後に200を返す型」をM08の設計判断に委ねた。M08は既存の`/api/ratelimit`のままとし、型は足さない（Q-811）。

## 5. 非機能要件、検証方法

### 5.1 非機能要件

| ID | 要件 |
| --- | --- |
| NFR-801 | 外部APIや実AWSへ接続しない。通信はすべてComposeの閉じたネットワーク内で行う。宛先は`api.example.com`などのダミー値とし、Squidのホワイトリストは変えない。 |
| NFR-802 | M01のサービス名、ポート、ネットワーク契約、M03のマッピングの契約、M06のTest Clientの出力契約を変えない。Test Client、Squid、Compose、既存マッピングへの変更を要しない構成とする（Q-812）。新規ファイルは`tests/m08-e2e-suite.sh`と`docs/E2Eテスト.md`、編集は`README.md`（参照1行）と`scripts/quality-gate.sh`（検査リストに1語）に限る。`test-client/`、`squid-config/`、`docker-compose.yml`、`wiremock-scenarios/`、`scripts/scenario-lib.sh`、`package.json`は変えない。 |
| NFR-803 | スイート全体の実行時間を抑える。429のシナリオは`Retry-After: 2`を3回待つため、待機だけで約6秒かかる。全体の目標は、待機を含めて60秒以内とする。Composeの起動待ちとビルドは含めない（Q-813）。待機だけの見積もりは約8秒（500後に成功が1秒、タイムアウトが1秒、429が6秒）である。目標は目安で、超えても失敗にはせず、所要時間をレポートの最後の行に出す。 |
| NFR-804 | 検査はPOSIX shで書き、新しい実行時依存を足さない。JSON解析にはM07と同じホストの`python3`を使う。M05〜M07の`trap`による後始末の方式を踏襲する。 |
| NFR-805 | スイートを連続で2回実行しても同じ結果になる（リセットが効いている証拠とする）。 |
| NFR-806 | 1台のWireMockに対して、シナリオを並列実行しない（M07のFR-712）。1スイートの中でも直列に実行する。 |
| NFR-807 | レポート、ログ、文書にAWSアカウントIDや認証情報を含めない。 |
| NFR-808 | 失敗の再現を、ログを読まなくてもシナリオ名から手元で再実行できる程度に支える。個別のシナリオは、モードの後の引数で指定する。例は`sh tests/m08-e2e-suite.sh smoke error-500-then-200`で、複数も指定できる。名前なしは4シナリオを既定の順（`normal`、`error-500-then-200`、`ratelimit-429`、`slow-5000`）で実行する（Q-814）。失敗時の再現コマンドは、この形で標準エラーに出す（FR-810）。 |

### 5.2 検証方法

検査入口は`tests/m08-e2e-suite.sh`とする（Q-804）。M06とM07と同じく、`unit`と`smoke`の2モードを持つ。引数なしは`smoke`とする。

| モード | 内容 |
| --- | --- |
| `unit` | Dockerを使わない。期待値表の解釈、レポートの組み立て、診断ログからの値の抽出、失敗時の出力形式を、スタブで確かめる。 |
| `smoke` | `unit`に続けてComposeを起動し、代表4シナリオを実通信で実行する。失敗の注入（意図的な期待値違反）で、再現用シナリオ名とログが出ることと、後始末が行われることを確かめる。 |

`slow-5000`はWireMockのジャーナル記録が遅れる可能性があるため、既定の順では最後に置く（Q-810）。
`unit`と`smoke`の詳細な内容は、planで確定する。

失敗の注入は、環境変数ではなく検査内のサブシェルで行い、本番のスクリプトにテスト専用の分岐を持ち込まない
（M07の方式と同じ）。

## 6. 対象外

- CIのスケジュール実行と成果物の保存（M09）
- GitHub Actionsのworkflow、`pnpm test`の整備（Q-804、M09）
- 実AWS、外部APIへの接続
- Test Client、Squid、Compose、既存マッピングの仕様変更
- WireMockの並列実行、動的ポート割り当て
- 503の`Retry-After`の尊重、タイムアウトのリトライ（M06の対象外を維持する）
- 4シナリオ以外の網羅的なパターン（M06の境界値の再検証は、M06の検査に任せる）
- ローカルとCIの最終受入検証（M11）
- `package.json`のscripts（`pnpm test`）の追加（M09）
- ルートの`plan.md`の2.6と`README.md`の表の書き換え（`docs/E2Eテスト.md`で違いを説明する。Q-815）
- `wiremock_count`の共通化（M06とM07の定義を、M08の検査入口へ複製する。Q-812）

## 7. 完了条件

- [ ] 正常、500後に成功、タイムアウト、429とバックオフの4シナリオが、一つのコマンドで自動実行される
- [ ] 各シナリオが、期待するステータス、リトライ回数、終了結果を検証している
- [ ] 外部APIや実AWSへ接続していない
- [ ] 失敗を意図的に起こすと、再現用のシナリオ名とログが出る
- [ ] 一つのシナリオが失敗しても残りが実行され、全体の終了コードが非ゼロになる
- [ ] テストレポートが出力される
- [ ] 失敗経路を含め、コンテナと一時ディレクトリが残らず、終了コードが保たれる
- [ ] スイートを連続で2回実行しても同じ結果になる
- [ ] M03〜M07の既存検査が引き続き通る
- [ ] M08のSpec Kit成果物と検証手順が保存されている
