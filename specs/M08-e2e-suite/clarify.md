### Q-802 503と遅延のどちらを必須とするか

| 項目 | 内容 |
| --- | --- |
| 選択肢A | `slow-5000`によるタイムアウトを必須とし、503は4シナリオに含めない |
| 選択肢B | 503を使うシナリオを追加する |
| 選択肢C | 両方を4シナリオの外に追加する |
| 決定 | 選択肢A（推奨案どおり） |
| 理由 | 503はタイムアウトにならない。`is_retryable_status`は503を5xxの再試行対象にし（`retry-lib.sh`の9〜12行）、`entrypoint.sh`は上限まで再試行して`retries_exhausted`で終わる（73〜75行）。Issueの「タイムアウト」を満たすのは遅延だけである |

503の再試行は、M06の`smoke`が`/api/error-503`で既に実機確認している（`tests/m06-client-resilience.sh`）。
M08は4シナリオに絞り、5シナリオ目は足さない。

### Q-806 失敗後も続けるか

| 項目 | 内容 |
| --- | --- |
| 選択肢A | 続ける。最後に全体の合否と失敗の一覧を出す |
| 選択肢B | 最初の失敗で止める |
| 決定 | 選択肢A（推奨案どおり）。ただし、リセットの確認に失敗したときだけ止める |
| 理由 | アサーションの失敗は、そのシナリオ固有の不具合として他と独立に扱える（FR-808）。一方、`wiremock_reset`か`wiremock_verify_reset`の失敗は環境の異常で、以降のシナリオの結果が信用できない |

リセット失敗時の扱いは次のとおり。

| 状況 | 扱い |
| --- | --- |
| 当該シナリオの開始前のリセット確認が失敗 | そのシナリオを実行せず、`FAIL`（未実行）として記録する。残りのシナリオは実行せず、`未実行`と記録する。終了コードは1 |
| アサーションが失敗 | そのシナリオを`FAIL`として記録し、次のシナリオを続ける。終了コードは最後に1 |

FR-807の「そのシナリオを実行せずにスイートを失敗にする」は、この扱いで満たす。FR-811の「残りは実行」は、
アサーションの失敗に限る旨をspec.mdに足す。

### Q-808 500後に成功するシナリオの待機

| 項目 | 内容 |
| --- | --- |
| 選択肢A | 既定の`RETRY_BACKOFF_BASE_SECONDS=1`のまま実行し、待機1秒を診断ログで確かめる |
| 選択肢B | 0に上書きして待機を省く |

### Q-809 タイムアウトのシナリオの応答タイムアウト

| 項目 | 内容 |
| --- | --- |
| 選択肢A | 2秒（spec.mdの推奨案） |
| 選択肢B | 1秒（M06の`smoke`と同じ） |
| 選択肢C | 3秒 |
| 決定 | 選択肢B（推奨案から変更） |
| 理由 | `delay-5000ms-case.json`の遅延は5000ミリ秒で、2秒でも1秒でも打ち切れる。M06の`smoke`が`RESPONSE_TIMEOUT_SECONDS=1`で終了コード28を実機確認済み（`tests/m06-client-resilience.sh`の561〜565行）。実機で確かめた値に合わせ、待機を1秒減らす |

この選択の影響は次のとおり。

| 項目 | 内容 |
| --- | --- |
| 打ち切りが遅延より前になる余裕 | 5000ミリ秒に対して1秒。余裕は4秒あり、環境が多少遅くても取り違えない |
| 接続タイムアウトとの関係 | 接続の既定は5秒で、`--max-time`の1秒が先に効く（`entrypoint.sh`の48行）。どちらで切れてもcurl終了コードは28で、区別しない（FR-606） |
| 所要時間 | 約1秒（待機1回） |

spec.mdの更新箇所はFR-804と4章の表で、`RESPONSE_TIMEOUT_SECONDS=1`に直す。

### Q-810 クライアント切断後のジャーナル

決定しない。plan工程の実機確認に移す。下の「plan以降の実機確認」の表に手順を残す。

決定の代わりに、次の暫定の扱いを置く。

| 項目 | 暫定の扱い |
| --- | --- |
| タイムアウトの必須の検証 | `CLIENT_ERROR=timeout`、終了コード28、標準出力が空、`result=timeout`、`attempts=1`。これらはジャーナルに依存しない |
| WireMockの受信回数 | 実機確認の結果が出るまで、必須としない。結果は`確認できる`、`確認できない`、`記録の時刻が遅れる`のいずれか |
| 確認できない場合 | 受信回数の検証を外し、`attempts=1`の診断ログを根拠にする。spec.mdのFR-804と4章の表から「WireMock受信1」を外す |
| 記録の時刻が遅れる場合 | 後述の混入の懸念を、planで対処する |

混入の懸念は次のとおり。`slow-5000`のクライアントは1秒で切断するが、WireMockはその時点で応答の遅延中の可能性がある。
ジャーナルへの記録が応答の完了時なら、約4秒後に、次のシナリオのリセットの後へ記録が入る。
`wiremock_verify_reset`はジャーナル全体の件数が0かを見る（`scripts/scenario-lib.sh`の257〜259行）ため、
次のシナリオの開始前確認が失敗する可能性がある。NFR-805（連続2回の実行）にも関わる。

### Q-811 429シナリオの形

| 項目 | 内容 |
| --- | --- |
| 選択肢A | 既存の`/api/ratelimit`（常に429）のまま、`retries_exhausted`を検証する |
| 選択肢B | 429の後に200を返す型を足す |
| 決定 | 選択肢A（推奨案どおり） |
| 理由 | `error-429-case.json`は常に429と`Retry-After: 2`を返す。Issueの対象は「429とバックオフ」であり、バックオフが働いた証拠（`retry_after=2 wait=2 capped=0`）は`retries_exhausted`でも得られる。型を足すとQ-812の「足さない構成」に反する |

細則は次のとおり。

| 項目 | 決定 |
| --- | --- |
| 総試行 | 4（`RETRY_MAX_ATTEMPTS_429`の既定3＋1。`retry-lib.sh`の128行、`entrypoint.sh`の84〜86行） |
| リトライ回数 | 3。診断ログの429の`retry`行が3本 |
| 待機 | 各回`retry_after=2 wait=2 capped=0`。合計6秒 |
| 終了コード | 0（`entrypoint.sh`の37行、M06のFR-611） |
| 期待値の持ち方 | 4と3は固定値でスイートに書く。M06の既定値が変わればスイートが失敗し、契約の変更を検知できる |

### Q-812 新しいシナリオ、スクリプト、設定を足さずに構成できるか

| 項目 | 内容 |
| --- | --- |
| 選択肢A | 既存のものだけで4シナリオを構成し、新規ファイルは検査入口と文書だけにする |

| 決定 | 選択肢A（推奨案どおり）。構成できることを読み取りで確認した |
| 理由 | 4シナリオの名前は`scenario_path`で全て引ける（`normal`、`error-500-then-200`、`slow-5000`、`ratelimit-429`）。上書きする環境変数は`RESPONSE_TIMEOUT_SECONDS`だけで、`docker-compose run -e`で渡せる（M06の561行と同じ） |

変更の範囲は次のとおり。

| 区分 | 対象 |
| --- | --- |
| 新規 | `tests/m08-e2e-suite.sh`、`docs/E2Eテスト.md` |
| 編集 | `README.md`（「Testing Scenarios」から文書への参照を1行）、`scripts/quality-gate.sh`（検査リストに1語） |
| 変更しない | `test-client/`、`squid-config/`、`docker-compose.yml`、`wiremock-scenarios/`、`scripts/scenario-lib.sh`、`package.json` |

`wiremock_count`は`scenario-lib.sh`に無く、M06とM07に同じ形で定義されている。
M08でも同じ関数を検査入口に複製する。`scenario-lib.sh`へ移すと、通っているM06とM07の検査を触る範囲が広がる。
重複の解消は、M08の対象外とする。

リセット直後はジャーナルが空なので、M08の`wiremock_count`は前後の差ではなく、実行後の絶対値を使える。

### Q-813 スイート全体の実行時間の目標

| 項目 | 内容 |
| --- | --- |
| 選択肢A | 待機を含めて60秒以内。Composeの起動待ちとビルドを除く |
| 選択肢B | 起動待ちを含めて60秒以内 |
| 決定 | 選択肢A（推奨案を、測る範囲を明確にして採る） |
| 理由 | 起動待ちとビルドは、イメージの取得状況や環境（Colimaなど）に左右され、M08の設計では制御できない。シナリオ本体は待機だけで決まる |

待機だけの見積もりは次のとおり。

| シナリオ | 待機 |
| --- | --- |
| 正常 | 0秒 |
| 500後に成功 | 1秒（Q-808） |
| タイムアウト | 1秒（Q-809） |
| 429 | 6秒（2秒×3回、Q-811） |
| 合計 | 約8秒 |

実行時間には、`docker-compose run`のコンテナ起動が4回分加わる。その実測値はplanの実機確認で取る。
目標は目安であり、超えても失敗にはしない（所要時間はレポートの最後の行に出すだけにする）。
実測値が60秒を超えたら、目標を見直すか、利用者に確認する。

### Q-814 個別のシナリオだけを実行する手段

| 項目 | 内容 |
| --- | --- |
| 選択肢A | 第1引数でシナリオ名を指定する（spec.mdの推奨案） |
| 選択肢B | 第1引数はモード（`unit`か`smoke`）のまま、第2引数以降でシナリオ名を指定する |
| 選択肢C | 環境変数で指定する |
| 決定 | 選択肢B（推奨案から変更） |
| 理由 | 第1引数をシナリオ名にすると、M06とM07で共通の`[unit\|smoke]`と食い違い、Q-804で決めた入口がそろわない。第1引数で未知の値を弾く規則（終了コード2）とも衝突する |

細則は次のとおり。

| 項目 | 決定 |
| --- | --- |
| 形 | `sh tests/m08-e2e-suite.sh smoke error-500-then-200`のように、モードの後に名前を並べる。複数も可 |
| 名前の検証 | `scenario_path`で引けない名前は、終了コード2で止まり、定義済みの一覧を出す（`scenario-lib.sh`の71〜75行） |
| 引ける名前でもE2Eの対象外 | `slow-100`など。標準エラーへ「4シナリオに含まれない」と一覧を出し、終了コード2 |
| 名前なし | 4シナリオを既定の順に実行する |
| 実行順 | 既定は`normal`、`error-500-then-200`、`ratelimit-429`、`slow-5000`。`slow-5000`を最後に置く理由はQ-810に残す。順は結果に影響しない（FR-808） |
| 失敗時の再現コマンド | `sh tests/m08-e2e-suite.sh smoke <シナリオ名>`の形で標準エラーに出す（FR-810） |
| `unit`と名前 | `unit`に名前を付けても無視せず、終了コード2で止める（意図しない指定を通さない） |

### Q-815 ルートの`plan.md`との食い違い

| 項目 | 内容 |
| --- | --- |
