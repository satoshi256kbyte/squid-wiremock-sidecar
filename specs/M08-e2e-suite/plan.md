# M08実装計画

## 1. 実装方針

M08は、M05の閉域経路、M06のTest Client、M07のシナリオ選択とリセットを組み合わせ、代表4シナリオを
一つのコマンドで実行して検証するスイートを足す。新規ファイルは検査入口`tests/m08-e2e-suite.sh`と
文書`docs/E2Eテスト.md`だけにする。Test Client、Squid、`docker-compose.yml`、既存マッピング、
`scripts/scenario-lib.sh`、`package.json`は変更しない（NFR-802、Q-812）。

シナリオの選択は`scripts/scenario-lib.sh`の`scenario_path`、リセットと確認は`wiremock_reset`と
`wiremock_verify_reset`をそのまま再利用する。`wiremock_count`は`scenario-lib.sh`に無く、
M06とM07に同じ形で定義されている。M08でも検査入口に複製し、共通化はしない（spec.md 6章）。

検証は、Dockerを使わない層とComposeを使う層に分ける。M06、M07と同じ`unit`と`smoke`の2モードで、
引数なしは`smoke`とする。本番のスクリプトにテスト専用の分岐は入れない。失敗の注入は、検査内のサブシェルで
関数を差し替えるか、本物の検査入口を子として起動して行う（M07の方式）。

## 3. 検査入口の構成

### 3.1 引数と終了コード

`sh tests/m08-e2e-suite.sh [unit|smoke] [シナリオ名...]`（FR-812、Q-814）。

| 引数 | 扱い | 終了コード |
| --- | --- | --- |
| なし | `smoke`で4シナリオを既定の順に実行 | 0または1 |
| `unit` | Dockerを使わない検査 | 0または1 |
| `smoke` | `unit`に続けてComposeで実行 | 0または1 |
| `unit`と名前 | 名前を無視せず、使い方を標準エラーへ出して止める | 2 |
| 不正なモード | 使い方を標準エラーへ出す | 2 |
| 未定義の名前 | `scenario_path`の終了コード2をそのまま返し、定義済みの一覧を出す | 2 |
| 定義済みだがE2E対象外（`slow-100`など） | 「4シナリオに含まれない」と対象4名を標準エラーへ出す | 2 |

引数の検証は、Composeの起動より前に行う。`scenario_path`は`set -e`の下で止まらないよう、
`if`の条件か`|| rc=$?`で呼ぶ。終了コードの意味は、0が全件合格、1が一つでも失敗、2が引数の誤りである。
シグナルによる中断は130（`INT`）と143（`TERM`）で、後始末の後にこの値で終わる（FR-813）。

### 3.2 シナリオ表

シナリオごとの条件と期待値は、`scenario_spec`という1つの関数に`case`で持つ。配列は使わない（POSIX sh）。
表の値はspec.md 4章に従う。`status`が出ないタイムアウトは`-`と書く。

| 名前 | パス | 上書きする設定 | 期待値の文字列 |
| --- | --- | --- | --- |
| `normal` | `/api/users/123` | なし | `status=200 result=success attempts=1 retries=0 wiremock=1 rc=0` |
| `error-500-then-200` | `/api/error-500-then-200` | なし | `status=200 result=success attempts=2 retries=1 wiremock=2 rc=0` |
| `ratelimit-429` | `/api/ratelimit` | なし | `status=429 result=retries_exhausted attempts=4 retries=3 wiremock=4 rc=0` |
| `slow-5000` | `/api/slow-5000` | `RESPONSE_TIMEOUT_SECONDS=1` | `status=- result=timeout attempts=1 retries=0 wiremock=1 rc=28`（`wiremock`はQ-810待ち） |

既定の順は`normal`、`error-500-then-200`、`ratelimit-429`、`slow-5000`とする。`slow-5000`を最後に置くのは、
応答の遅延中の記録が次のシナリオへ混ざる懸念（Q-810）を避けるためである。名前を指定した場合は、指定の順に実行する。
パスと名前の対応は`scenario_path`で引き、表のパスと一致することを`unit`で確かめる。
パスを入口に二重に書かず、`scenario_path`の結果を使う。表に持つのは上書き設定と期待値だけにする。

429の総試行4とリトライ3は固定値で書く（Q-811）。`unit`で、`retry-lib.sh`の
`RETRY_MAX_ATTEMPTS_429`の既定値（`apply_config_defaults`をサブシェルで呼んで読む）に1を足した値が4であることと、
既定値そのものが3であることを確かめる。M06の既定値が変わると、`unit`の段階で契約の変更に気づける。

### 3.3 関数の分担

| 関数 | 役割 |
| --- | --- |
| `scenario_spec` | 名前から、パス、上書き設定、期待値の文字列を返す |
| `parse_client` | 標準出力と標準エラーのファイルから、実測値の文字列を組み立てる（3.4） |
| `extra_checks` | シナリオ固有のログ検査。診断ログの待機行、標準出力が空であること（3.5） |
| `wiremock_count` | M06、M07と同じ定義の複製。パスの受信回数を読む |
| `run_client` | `docker-compose run --rm --no-deps -e TEST_API_PATH=<パス> -e 名前=値 ... test-client`を1回実行し、出力を別ファイルに残す。パスは`-e TEST_API_PATH=`で必ず渡す |
| `run_one` | 1シナリオの実行。クライアント実行、実測、比較、結果の記録。期待値の`wiremock`が`-`なら`wiremock_count`を呼ばない（3.4） |
| `run_suite` | リセット、実行、続行と停止の判断を繰り返し、レポートを出す（5章） |
| `report_row`、`report_summary` | 標準出力の表の組み立て（5.3） |
| `fail_detail` | 失敗したシナリオの再現情報と診断ログを標準エラーへ出す（5.4） |

`run_suite`が外部へ触る3点（リセット確認、クライアント実行、受信回数の読み取り）は、それぞれ`suite_reset`、
`run_client`、`wiremock_count`の関数経由にする。`unit`は、この3関数をサブシェル内で差し替えてスタブにする。
本番の関数に差し替え用の分岐は入れない。

### 3.4 実測値の取り方

| 項目 | 取り方 |
| --- | --- |
| `status` | 標準出力の`CLIENT_STATUS=`行。無ければ`-` |
| `result`と`attempts` | 標準エラーの`CLIENT_DIAG result=`行。`success`、`retries_exhausted`は`status=`を伴い、`timeout`は`curl_exit=28`を伴う |
| `retries` | 標準エラーの`CLIENT_DIAG retry attempt=`行の数。総試行−1とも突き合わせる（3.5） |
| `wiremock` | リセット直後の絶対値。`wiremock_count <パス>`をクライアント実行の直後に読む |
| `rc` | `run_client`が残したクライアントの終了コード |

期待値の`wiremock`が`-`のシナリオでは、`wiremock_count`を呼ばず、実測も`wiremock=-`とする。
期待値が数値のシナリオだけ、`wiremock_count`の結果を使う。

期待値と実測値は同じ項目名の文字列にして、文字列の等しさで合否を決める。値が読み取れない項目は`-`を入れ、
期待値と一致しない扱いにする（読み取れないことを合格にしない）。

### 3.5 シナリオ固有の検査

文字列の比較に加えて、次のログの検査を行う。どれも`CLIENT_DIAG`と標準出力だけを見る。Test Clientの契約は変えない（FR-806）。

| シナリオ | 検査 |
| --- | --- |
| すべて | 診断ログの`retry`行の数が総試行−1に等しい |
| `error-500-then-200` | 診断ログに`CLIENT_DIAG retry attempt=1 status=500 class=5xx retry=1/3 wait=1`の行がある（Q-808） |
| `ratelimit-429` | `class=429`の`retry`行が3本あり、すべてが`retry_after=2 wait=2 capped=0`を含む |
| `slow-5000` | 標準出力が空である。標準エラーに`CLIENT_ERROR=timeout`の行がある |

## 4. 検証境界

| 層 | 対象 | Compose |
| --- | --- | --- |
| `unit` | 引数の検査、期待値表、実測値の抽出、レポートの形式、失敗出力、続行と停止の判断、文書の内容 | 使わない |
| `smoke` | `unit`に続けて、Composeを起動した実通信、連続2回、失敗経路の回収、残存の確認 | 使う |

Composeを使うのは`smoke`だけである。`unit`は、`docker-compose`が`PATH`に無い環境でも通る。

### 4.1 `unit`

Dockerとネットワークを使わない。リポジトリのファイルは書き換えない。一時ファイルは`mktemp -d`で作り、`trap`で消す。

| 検査 | 内容 |
| --- | --- |
| 引数 | 不正なモード、`unit`に名前、未定義の名前、対象外の名前が終了コード2。名前なしの既定の順 |
| 期待値表 | 4名が`scenario_path`で引ける。期待値の文字列が3.2の表と同じ。429の4と3が`retry-lib.sh`の既定と整合する |
| 抽出 | 成功、500後の成功、429の上限到達、タイムアウトの4種の標準出力と標準エラーの例から、実測値の文字列を組み立てる。読み取れない場合は`-` |
| 固有の検査 | 3.5の検査が、正しい例では通り、1語だけ崩した例（待機が`wait=2`、`capped=1`、標準出力が空でない）では落ちる |
| レポート | 1シナリオ1行、4項目、`PASS`と`FAIL`。最後の行に全体の合否、合格数と失敗数、失敗名の一覧、秒数がある。ファイルを作らない |
| 失敗出力 | シナリオ名、パス、上書き設定の名前と値、再現コマンド、診断ログが標準エラーにある。値に認証情報の形（`Authorization`、`Bearer`、12桁の数字、`arn:aws`）がない |
| 続行と停止 | スタブで、3番目のシナリオだけ不一致にしても4番目まで実行され、終了コード1になる。3番目のリセット確認を失敗させると、3番目は`FAIL`（未実行）、4番目は`未実行`でクライアントが呼ばれず、終了コード1になる |
| 順序の独立 | スタブで実行順を逆にしても、各シナリオの合否が変わらない（FR-808） |
| Composeを呼ばない | `docker-compose`を`PATH`から外した環境で`unit`が通る |
| 文書 | `docs/E2Eテスト.md`の必須の節、`README.md`の参照、識別情報の不在（9章） |

### 4.2 `smoke`

`unit`が落ちたらComposeを起動しない。起動、準備完了の待機、後始末はM07の`smoke_run`と同じ方式にする。

| 順 | 検査 |
| --- | --- |
| 1 | 開始前のリセットと確認 |
| 2 | 周1: `run_suite`で4シナリオを既定の順に実行し、4行すべてが`PASS`、終了コード0であること |
| 3 | 周2: 同じ起動のまま、もう一度`run_suite`を実行し、レポートの各行が周1と同じであること（NFR-805）。所要時間の行は比べない |
| 4 | 名前指定: `smoke error-500-then-200`の形で、1シナリオだけを`run_suite`で実行し、1行のレポートになること（NFR-808） |
| 5 | 失敗の注入（6章）: アサーション失敗の続行、リセット確認失敗の停止 |
| 6 | 終了後に`docker-compose down`し、`docker-compose ps -a -q`が空であること |
| 7 | 失敗経路の子の起動（6章）: Compose起動失敗、`INT`、`TERM` |

周1と周2は、`run_suite`を2回呼ぶ。スクリプトを再起動しない。再起動した2回の実行は、U11で手動で確かめる。

## 5. スイートの実行

### 5.1 実行ループ

シナリオごとに、次を順に行う（FR-801、FR-807、FR-808、NFR-806）。直列で、並列には実行しない。

1. `wiremock_reset`と`wiremock_verify_reset`を呼ぶ（`suite_reset`）
2. 失敗したら、そのシナリオを`FAIL`（未実行）として記録し、残りを`未実行`として記録して、ループを抜ける
3. `run_client`でTest Clientを1回実行する。`-e TEST_API_PATH=<scenario_pathの結果>`と、上書き設定を`-e 名前=値`で渡す
4. `wiremock_count`で受信回数を読み、3.4の実測値を組み立てる。ただし期待値の`wiremock`が`-`のシナリオでは読まず、`wiremock=-`とする
5. 期待値と比べ、3.5の検査を行い、`PASS`か`FAIL`を記録する。`FAIL`でも次のシナリオへ進む（FR-811）

ホストの環境変数は`docker-compose.yml`の`environment`に無いので、コンテナには渡らない。
上書きするのは、`docker-compose run -e`で明示した変数だけである。リトライの設定は既定値を使う。

終了時は、1つでも`FAIL`か`未実行`があれば1、すべて`PASS`なら0とする。

### 5.2 シナリオごとの時間

`date +%s`でシナリオの開始と終了を取り、標準エラーに`scenario <名前> elapsed=<秒>`を出す。
`$SECONDS`はPOSIX shにないため使わない。レポートの所要時間は、最初のシナリオの開始から最後のシナリオの終了まで
とし、Composeの起動待ちとビルドを含めない（NFR-803、Q-813）。60秒を超えても失敗にはしない。

### 5.3 レポート

標準出力へ、表形式のテキストで出す（FR-809）。ファイルは作らない。区切りは` | `にする。

```text
scenario | expected | actual | result
normal | status=200 result=success attempts=1 retries=0 wiremock=1 rc=0 | status=200 ... rc=0 | PASS
...
summary: FAIL passed=3 failed=1 not_run=0 failed_scenarios=ratelimit-429 elapsed=12s
```

最後の行は、全体の合否、合格数と失敗数と未実行数、失敗名の一覧、所要時間（秒）を含む。失敗がなければ一覧は`-`とする。
リセット確認に失敗したシナリオの行は、`result`を`FAIL`、`actual`を`not_run`と書き、失敗数に数える。
後続の`未実行`のシナリオは、`result`を`NOT_RUN`、`actual`を`not_run`とし、失敗数に数えず`not_run=`に数える。
一方で全体は`FAIL`にする。
`passed + failed + not_run`は、実行対象の数に等しい。

### 5.4 失敗時の出力

`FAIL`のたびに、標準エラーへ次を出す（FR-810、NFR-808）。

| 項目 | 内容 |
| --- | --- |
| 再現用のシナリオ名 | `scenario: <名前>` |
| 条件 | パス、上書きした環境変数の名前と値（`RESPONSE_TIMEOUT_SECONDS=1`など。上書きがなければ`none`） |
| 再現コマンド | `sh tests/m08-e2e-suite.sh smoke <名前>` |
| 診断ログ | そのシナリオの標準エラー全体（`CLIENT_DIAG`の行） |
| 差分 | 失敗した検査の名前と、期待値と実測値 |

コンテナのログは、後始末の`cleanup`が終了コードが0以外のときに、`docker-compose logs --no-color --tail 100 squid wiremock`
で標準エラーへ出す（M07と同じ）。1回の実行で1度だけ出る。診断ログとコンテナログに、認証情報は含まれない
（通信はダミーの`api.example.com`のみ、`Authorization`ヘッダーを送らない）。

## 6. 失敗の注入、後始末

### 6.1 後始末（`trap`の順序）

`smoke`の`cleanup`は、M07の`smoke_run`と同じ順序にする。`EXIT`で`cleanup`、`INT`で`exit 130`、`TERM`で`exit 143`を
トラップし、シグナルも`EXIT`の後始末を通す。`cleanup`の先頭で`rc=$?`を取り、最後に`exit "$rc"`で元の終了コードを保つ（FR-813）。

| 順 | 処理 | 失敗時の扱い |
| --- | --- | --- |
| 1 | `rc=$?`を保存 | なし |
| 2 | `rc`が0以外ならコンテナのログを標準エラーへ出す | 失敗しても続ける（`\|\| true`） |
| 3 | `cleanup: reset attempted`を標準エラーへ出し、`wiremock_reset`を試み、`cleanup: reset ok`か`cleanup: reset failed (ignored)`を出す | 失敗は無視し、Composeの回収を妨げない |
| 4 | `docker-compose down --remove-orphans` | 失敗しても続ける |
| 5 | 一時ディレクトリの削除 | 失敗しても続ける |
| 6 | `exit "$rc"` | 元の終了コードを返す |

`unit`だけの実行では、Composeを起動しないため、`trap`は一時ディレクトリの削除だけを行う（M07と同じ）。
開始前にも`docker-compose down --remove-orphans`を呼び、前回の残りを混ぜない。

### 6.2 リセット確認の失敗

| 場面 | 扱い |
| --- | --- |
| スイートの途中の`suite_reset`が失敗 | 5.1の手順2のとおり、当該を`FAIL`（未実行）、残りを`未実行`、終了コード1。ループは続けない |
| 後始末の`wiremock_reset`が失敗 | 無視する。ログに`cleanup: reset failed (ignored)`を残し、`down`は必ず呼ぶ |
| `slow-5000`の後の遅れた記録でリセット確認が失敗 | 7.3の分岐に従う。混入が確認された場合のみ、`slow-5000`の後に待機を入れる |

### 6.3 失敗の注入

#### アサーション失敗（続行）

`smoke`の検査内のサブシェルで、`scenario_spec`の期待値を差し替え、本物の`run_suite`を実通信で実行する。
例えば`normal`の総試行を2と期待させ、続けて`error-500-then-200`は正しい期待値のままにする。

| 確認 | 内容 |
| --- | --- |
| 終了コード | 1 |
| レポート | `normal`が`FAIL`、`error-500-then-200`が`PASS`（残りが実行された） |
| 標準エラー | シナリオ名`normal`、再現コマンド、`CLIENT_DIAG result=success attempts=1`の診断ログがある |

#### リセット確認の失敗（停止）

サブシェルで`wiremock_verify_reset`を、1回目は成功、2回目は失敗に差し替える。`smoke`と`unit`の両方で行う
（`unit`はクライアントもスタブにする）。

| 確認 | 内容 |
| --- | --- |
| 終了コード | 1 |
| レポート | 1番目は実行され`PASS`、2番目は`FAIL`（未実行）、3番目以降は`NOT_RUN` |
| クライアント | 2番目以降で呼ばれていない（スタブの呼び出し記録、または`wiremock_count`が増えないこと） |

#### Compose起動失敗

本物の検査入口を子として起動し、`COMPOSE_FILE`に存在しないファイルを渡す。`docker-compose up`が失敗して終了コード1になり、
`cleanup`が走る。`COMPOSE_FILE`は`docker-compose`の標準の環境変数で、本番のスクリプトに分岐を足さない。

| 確認 | 内容 |
| --- | --- |
| 終了コード | 1が保たれる |
| 標準エラー | `cleanup: reset attempted`がある。リセットは失敗するが無視されている |
| 回収 | 子の一時ディレクトリが空。`docker-compose ps -a -q`（親のComposeファイル）が空 |

親のスタックは、子の起動前に`down`済みにする（M07と同じ）。

#### `INT`と`TERM`

M07の`smoke_child_signal`と同じく、Pythonで子を起動し、管理APIが応答してから`SIGINT`か`SIGTERM`を送る。
子の信号の既定の動作は`preexec_fn`で戻す（バックグラウンドのシェルは`INT`を無視するため）。

| 信号 | 期待する終了コード | 確認 |
| --- | --- | --- |
| `INT` | 130 | `cleanup: reset attempted`がある。コンテナの残存と一時ディレクトリがない |
| `TERM` | 143 | 同上 |

子には、再帰を防ぐための`M08_NESTED=1`を渡す。子の中では失敗経路の検査を行わない。この変数は再帰を止める以外の
挙動を変えない（M07の`M07_NESTED`と同じ）。`sh`は前景のコマンドが終わるまでトラップを処理しないため、
子の待機は`sleep`の短い間隔のポーリングにする。検査全体に上限時間を設け、超えたら子を`kill`して失敗にする。

## 7. Q-810の実機確認

クライアントが1秒で切断した後も、WireMockのジャーナルに`slow-5000`の受信が残るか、いつ記録されるかを確かめる。
結果で、`slow-5000`の`wiremock`の期待値と、次のシナリオへの混入への対処が決まる。
このため、実装単位の最初（U1）に置き、結果が出るまで`slow-5000`の行の期待値と、5.1の手順4の細部を確定しない。
planでは実験を行わない。実験は実装段階で、手動で1回だけ行う。`smoke`には入れない。

### 7.1 準備

M07の実験と同じく、`$KIROCREW_SCRATCH`配下の使い捨てコピーで行い、リポジトリは書き換えない。

1. `docker-compose.yml`、`Dockerfile.test-client`、`squid-config/`、`wiremock-scenarios/`、`test-client/`、
   `scripts/scenario-lib.sh`をコピーに複製する
2. ポート3128と8080が空であることを確かめる。空でなければ止めて報告する
3. プロジェクト名を明示して起動する（`docker-compose -p m08-q810 up -d --build squid wiremock`）。M07と同じく、
   `colima status`を確認し、`DOCKER_HOST`を設定する
4. `wiremock_reset`と`wiremock_verify_reset`が通ることを確かめる

実験の前後で、リポジトリの`git status --short`が変わらないことを確かめる。

### 7.2 手順と観測

クライアントは次の形で実行する。`T0`は、クライアントが終了した（終了コード28を返した）時刻とする。

```sh
docker-compose -p m08-q810 run --rm --no-deps \
  -e TEST_API_PATH=/api/slow-5000 -e RESPONSE_TIMEOUT_SECONDS=1 test-client
```

| 実験 | 操作 | 観測 |
| --- | --- | --- |
| E1 記録の有無と時刻 | リセット後にクライアントを実行する。`T0`から1秒おきに、`T0+10`秒まで、`/__admin/requests/count`（`/api/slow-5000`）と`GET /__admin/requests`の`meta.total`を読む | 件数が1になる最初の秒。`T0`で既に1か、遅れて1になるか、1にならないか |
| E2 記録の中身 | 件数が1になったら、`/__admin/requests`のそのエントリの`wasMatched`、`response.status`、`loggedDate`を保存する | 遅れて記録される場合、応答が200で完了した後の記録か |
| E3 リセットへの混入 | リセット後にクライアントを実行し、`T0`の直後に`wiremock_reset`と`wiremock_verify_reset`を呼ぶ。その後`T0+10`秒まで、1秒おきに件数を読み、最後に`wiremock_verify_reset`をもう一度呼ぶ | 直後の確認の結果。リセット後に件数が1へ戻るか。最後の確認が失敗するか |
| E4 安定性 | E1を連続で3回行う | 3回で結果が同じか |
| E5 ほかへの影響 | E3の後で、`normal`を実行して`wiremock_count /api/users/123`と`wiremock_verify_reset`を読む | 遅れた記録が他のパスの件数を乱さないか |

結果は`specs/M08-e2e-suite/q810-experiment.md`に日本語で記録する。節は環境、手順、観測（各実験の秒ごとの値）、
分岐の決定、後続への影響とする。実験の終了後は`docker-compose -p m08-q810 down --remove-orphans`で回収し、コピーを削除する。

| 結果 | 判定の条件 | 決まること |
| --- | --- | --- |
| 即時に記録される | E1で`T0`に件数が1で、E4の3回とも同じ。E3の最後の確認も通る | `wiremock=1`を維持する。待機は入れない。`slow-5000`を最後に置く既定の順だけを残す |

## 12. リスク

| リスク | 対策 |
| --- | --- |
| `slow-5000`の記録が次のシナリオへ混ざる | U1で確かめる。既定の順で最後に置き、遅れる場合は待機を入れる（7.3） |
| `slow-5000`が切断後に記録されない | 受信回数の検証を外し、`attempts=1`の診断ログを根拠にする（7.3） |
| 429の待機で全体の時間が延びる | 待機だけで約8秒。目標60秒は目安で、超えても失敗にしない（5.2） |
| 診断ログの書式をM06が変える | `unit`の抽出と固有の検査が落ちて気づける。M06の契約は変えない |
| 429の既定値をM06が変える | 固定値とのずれを`unit`で検知する（3.2） |
| `wiremock_count`の複製が、M06とM07の定義とずれる | 共通化しない方針のため、一致の検査は置かない。M08の`unit`は自分の定義だけを確かめ、差が出たらM08側で独立に直す |
| `INT`と`TERM`で子がすぐ終わらず検査が固まる | 子はポーリング待機にし、全体に上限時間を設ける（6.3） |
| 失敗経路の検査が残骸を残す | 親の`trap`でも子のコンテナと一時ディレクトリを回収する。終了後に`ps -a -q`で確かめる |
| 品質ゲートの時間が増える | 実測してから登録を判断する（10章） |
| 公開物にアカウントIDや認証情報が混ざる | 文書と出力はダミー値だけにする。`unit`で`grep`する（NFR-807） |

## 13. 制約

- `test-client/`、`squid-config/`、`docker-compose.yml`、`wiremock-scenarios/`、`scripts/scenario-lib.sh`、`package.json`を変更しない
- 本番のスクリプトにテスト専用の分岐を入れない。再帰を防ぐ`M08_NESTED`だけを例外とし、挙動を変えない
- 検査はリポジトリのファイルを書き換えない。一時ファイルは`mktemp -d`で作り、`trap`で消す
- 外部ネットワークへ出ない。通信は閉じたネットワークと`127.0.0.1`だけ
- 1台のWireMockに対して並列に実行しない
- レポートはファイルに保存しない（M09の対象）
