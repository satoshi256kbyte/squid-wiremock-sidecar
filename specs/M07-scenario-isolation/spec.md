# M07 シナリオ切り替えとテスト隔離の仕様

## 1. 目的

WireMockの応答シナリオを名前で明示的に選べるようにし、テスト間で状態が漏れない隔離手順を固定する。
M06が別途とした「500の後に200を返すリトライ成功」を再現し、後続のM08（代表4シナリオのE2E）が再利用できる土台にする。

要件の出典はIssue #7とし、FR-709とFR-710はspec.mdが追加した（clarify決定、Q-701）。
spec.mdがIssue #7より厳しい箇所（初期化の対象にジャーナルとシナリオ状態を含める、リセットの確認、
`INT`と`TERM`での回収）は意図して残す。

## 2. 対象範囲

- シナリオ名による選択（正常、500後に200、429、遅延）
- WireMockの状態（マッピング、リクエストジャーナル、シナリオ状態）のリセット
- テスト開始前と終了後のリセット、および失敗経路でのコンテナと一時データの回収
- シナリオをJSONファイル単位で追加する手順の文書化（`docs/シナリオ隔離.md`）
- `README.md`の「Testing Scenarios」から`docs/シナリオ隔離.md`への参照の追加
- 1台のWireMockに対してテストを並列実行しないという規則の明文化
- `POST /__admin/reset`の効果の実機実験と、その記録（`specs/M07-scenario-isolation/reset-experiment.md`）
- `scripts/quality-gate.sh`の検査リストへの`tests/m07-scenario-isolation.sh`の登録

状態を持たないシナリオは1ファイル、状態遷移を持つシナリオは状態ごとに1ファイルで追加する
（clarify決定・要確認、Q-705）。

## 3. 機能要件

| ID | 要件 |
| --- | --- |
| FR-701 | シナリオを名前で明示的に選択できる。名前の形式は`^[a-z0-9][a-z0-9-]*$`とし、各スタブマッピングのトップレベル`name`フィールドに保持する。`mappings/*.json`を読み、`name`が一致するスタブの`request.urlPath`を宛先として返す（Docker不要）。同じ名前は同じ`method`と`urlPath`に限り、異なるパスに現れたら検査で失敗させる。未定義の名前は標準エラーへ`unknown scenario: <名前>`と定義済みの名前一覧を出し、終了コード2で終了する。既定シナリオへ黙ってフォールバックしない（clarify決定、Q-702） |
| FR-702 | 正常シナリオ（`normal`）は、M03の`/api/users/123`と同じ200とJSON本文を返す |
| FR-703 | 「500の後に200」シナリオ（`error-500-then-200`）は、パス`/api/error-500-then-200`で初回が500、2回目以降が200を返す。状態ごとに1ファイルの2ファイル構成とする。`error-500-then-200-1.json`は`scenarioName`が`error-500-then-200`、`requiredScenarioState`が`Started`、`newScenarioState`が`Succeeded`、500と`error-500.json`を返す。`error-500-then-200-2.json`は同じ`method`と`urlPath`と`scenarioName`、`requiredScenarioState`が`Succeeded`、`newScenarioState`なし、200と`success.json`を返す。`__files/`は既存のものを再利用する。M06のTest Clientを`TEST_API_PATH=/api/error-500-then-200`で実行し、`CLIENT_STATUS=200`、最終結果`success`、総試行2回を確認する（clarify決定、Q-705、Q-706） |
| FR-704 | 429シナリオ（`ratelimit-429`）は、既存の`/api/ratelimit`を流用し、429と`Retry-After: 2`を返す。`Retry-After`の値は変更しない。M06の`Retry-After`尊重を、診断ログの待機時間と`wiremock_count`で実通信により確認できる（clarify決定、Q-707） |
| FR-705 | 遅延シナリオは、M03の100ms（`slow-100`）と5000ms（`slow-5000`）を名前で選べる。M06のタイムアウト検証で使える |
| FR-706 | あるシナリオの実行が、別のシナリオ、または同じシナリオの次回実行の応答を変えない。「500の後に200」を2回続けて実行しても、2回とも初回は500になる |
| FR-707 | 各テストの開始前に、マッピング、リクエストジャーナル、シナリオ状態をWireMockの管理APIで初期状態へ戻す。ファイル置換は使わない。具体的な呼び出し列はplanで確定する（clarify決定・要確認、Q-703、Q-704） |
| FR-708 | 各テストの終了後にも同じリセットを行う。テストが失敗した場合も、後始末でリセットを試みる。失敗時の後始末でリセットを試みたことは、標準エラーの記録で確認できる。 |
| FR-709 | リセット後に初期状態を確認する。確認手段と項目は、マッピング一覧（`GET /__admin/mappings`）の件数が`wiremock-scenarios/mappings/*.json`のファイル数（`.gitkeep`を除く）と一致すること、ジャーナル（`GET /__admin/requests`）の件数が0であること、シナリオ一覧（`GET /__admin/scenarios`）の状態がすべて`Started`であること。不一致なら終了コード非ゼロで停止し、続行しない。管理APIの応答のフィールド名は実機の応答で確認してからパース方法を固定する。確認は`smoke`で行う（clarify決定、Q-703、Q-705） |
| FR-710 | 失敗経路（アサーション失敗、`INT`、`TERM`）でも、Composeのコンテナと一時ディレクトリを回収する。終了コードは元の失敗を保ち、回収後に`docker-compose ps -a -q`が空である。終了コードの期待値は`INT`が130、`TERM`が143とし、plan以降の実機確認項目とする（観測値が異なれば、実測値でこの要件を直す）（clarify決定、Q-709） |
| FR-711 | シナリオをJSONファイル単位で追加する手順を`docs/シナリオ隔離.md`に文書化する。状態を持たないシナリオは1ファイル、状態遷移を持つシナリオは状態ごとに1ファイルとする。手順にはファイルの置き場所（`wiremock-scenarios/mappings/`と`__files/`）、必須項目、状態を持つ場合の書き方、検証方法を含め、アプリケーションコードの変更を要しない（clarify決定・要確認、Q-705、Q-708） |
| FR-712 | 1台のWireMockに対して複数のテストを並列実行しないことと、その理由を`docs/シナリオ隔離.md`に明記する（clarify決定・要確認、Q-708） |

## 4. 並列実行しない理由

次の状態は、WireMockインスタンスと実行環境で共有される。並列に走らせるとテストが互いの結果を壊す。

| 共有されるもの | 並列時の影響 |
| --- | --- |
| シナリオ状態 | 一方のリクエストが「500の後に200」の状態を進め、他方の初回が200になる |
| リクエストジャーナル | M06の`wiremock_count`のような件数検査が、他方の呼び出しを数える |
| リセット操作 | 一方のリセットが他方の実行中のマッピングと状態を消す |
| ホストのポートとコンテナ | `docker-compose.yml`は3128と8080を固定で公開する。後始末の`docker-compose down`は他方のコンテナも落とす |

## 5. シナリオ契約、非機能要件、検証方法

### 5.1 シナリオ契約

名前から宛先パスを引く対応は次のとおり。M03のパス契約は変えない（clarify決定、Q-702）。

| 名前 | パス | 由来 |
| --- | --- | --- |
| `normal` | `/api/users/123` | M03の`normal-case.json`に`name`を足す（clarify決定・要確認） |
| `error-500-then-200` | `/api/error-500-then-200` | 新規（2ファイル構成、FR-703） |
| `ratelimit-429` | `/api/ratelimit` | M03の`error-429-case.json`に`name`を足す（clarify決定・要確認） |
| `slow-100` | `/api/slow-100` | M03の`delay-100ms-case.json`に`name`を足す（clarify決定・要確認） |
| `slow-5000` | `/api/slow-5000` | M03の`delay-5000ms-case.json`に`name`を足す（clarify決定・要確認） |

`/api/error-500`と`/api/error-503`には`name`を付けない（clarify決定・要確認）。M07の4シナリオに含まれず、
付けるとM03のファイルへの変更が増える。必要になったら1行足すだけで選択できる。

新しいパスにSquid設定の変更は要らない。Squidはドメインで判定し、パスでは判定しない。

### 5.2 非機能要件

| ID | 要件 |
| --- | --- |
| NFR-701 | M03のマッピングの契約（パス、ステータス、ヘッダー、本文、遅延）を変えない。M03のファイルへ`name`を足す変更は契約を変えない（clarify決定・要確認）。1ファイル1マッピングの規約を維持する。`/api/error-500`は常に500を返し、M06の呼び出し回数検査（1回から4回）を保つ |
| NFR-702 | M01のサービス名、ポート、ネットワーク契約を変更しない。`docker-compose.yml`は変更せず、`:ro`マウントも変えない（clarify決定、Q-704）。Squid設定は、キャッシュを無効にする`cache deny all`の1行の追加だけを許す。理由は、キャッシュがWireMockのシナリオ状態の変化を古い応答で隠し、FR-706を満たせないため（2026-11-03、利用者が承認。T707の実機確認で判明） |
| NFR-703 | シナリオの追加と変更にアプリケーションコードの変更を要しない（M03のNFR-301を継承する） |
| NFR-704 | 検査と名前解決の関数（`scripts/scenario-lib.sh`）はPOSIX shで書き、新しい実行時依存を足さない。JSON解析にはM03と同じホストの`python3`を使う。後始末の方式はM06のスモークと同じ`trap`とする（clarify決定、Q-702、Q-709） |
| NFR-705 | 検査を連続で2回実行しても同じ結果になる（リセットが効いている証拠とする）。`smoke`の最後に確かめる |
| NFR-706 | 文書、ログ、検査出力にAWSアカウントIDや認証情報を含めない。例にはダミー値（`api.example.com`など）を使う |

### 5.3 検証方法

検査入口は`tests/m07-scenario-isolation.sh`とし、M06と同じ`unit`と`smoke`の2モードを持つ。既定は`smoke`
（clarify決定、Q-709）。

| モード | 内容 |
| --- | --- |
| `unit` | Dockerを使わない。名前の解決（未定義の名前は終了コード2）、名前の形式と重複、状態を持つグループの静的検査、追加手順の検査。文書の並列禁止の節と識別情報の混入を確かめる |
| `smoke` | `unit`に続けてComposeを起動し、リセットと確認（FR-709）、対照実験、「500の後に200」の通し実行、4シナリオの応答、失敗経路の回収、連続2回実行を確かめる |

`unit`の状態を持つグループの静的検査は次のとおり（clarify決定、Q-705、Q-706）。

| 検査 | 内容 |
| --- | --- |
| 状態の網羅 | `scenarioName`を持つグループに、`requiredScenarioState`が`Started`のスタブがちょうど1つある |
| 遷移の到達性 | `newScenarioState`の値は、同じグループのどれかの`requiredScenarioState`に現れる |
| 宛先の一致 | 同じグループのスタブは同じ`method`と`urlPath`を持つ |
| 名前の一致 | 同じ`scenarioName`のスタブは同じ`name`を持つ |
| 部分指定 | `requiredScenarioState`を持つのに`scenarioName`が無いスタブを拒否する |
| パスの重複 | 全スタブの`method`と`urlPath`の組が、シナリオグループの外で重複しない |

これらはM03の検査とは別に置き、M03のファイルは変更しない。

追加手順の検査は、`unit`で`wiremock-scenarios/`を`mktemp -d`の一時ディレクトリへコピーし、
手順どおりに1ファイルを足して、名前の解決と静的検査が通ることを確かめる。リポジトリのファイルは書き換えない。

`smoke`の主な検査は次のとおり。

- 対照実験として、`error-500-then-200`をリセットなしで2回続けて呼ぶと2回目が初回から200になり、
  リセットを挟むと初回が500に戻ることを示す（状態漏れの再現と解消）。
- `/__admin/mappings`の`name`と`request.urlPath`が、ファイルから引いた結果と一致する。
- アサーション失敗、`INT`、`TERM`で、`docker-compose ps -a -q`が空になり、一時ディレクトリが残らず、
  終了コードが元の失敗を保つ。失敗の注入は環境変数ではなく検査内のサブシェルで行い、
  本番のスクリプトに分岐を持ち込まない。
- Squid経由で新しいパスに到達できる。

`scripts/quality-gate.sh`の検査リストに、M06の後ろへ`tests/m07-scenario-isolation.sh`を登録する（plan 7.3）。

## 6. 対象外

- 1台のWireMockを共有する並列ジョブ（並列化する場合はテストごとに別のComposeプロジェクトと別ポートを使う設計が要るため別途）
- Test Clientコードの変更（M06の契約を維持する）
- 4シナリオのE2Eテスト本体（M08）
- Squid、Composeのサービス構成の変更
- WireMock拡張、レスポンステンプレート、動的ポート割り当て
- `:ro`マウントの変更、ホスト側ファイルの書き換えによる初期化（clarify決定・要確認、Q-704）
- 複数スタブ形式（`mappings`配列）とM03の検査の拡張（clarify決定、Q-705）
- 429の後に200を返す型（必要ならM08の設計で判断し、FR-711の手順で1つ足す。clarify決定、Q-707）
