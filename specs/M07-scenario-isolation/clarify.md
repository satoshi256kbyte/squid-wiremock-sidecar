## 前提

リポジトリの読み取りで確認できた事実と、実機でしか確認できない事項を分けて扱う。

| 区分 | 内容 |
| --- | --- |

| 項目 | 内容 |

### Q-703 `POST /__admin/reset`の効果

| 項目 | 内容 |
| --- | --- |
| 選択肢A | `POST /__admin/reset`の1回で、マッピング、ジャーナル、シナリオ状態を戻す前提にする |
| 選択肢B | マッピング、ジャーナル、シナリオ状態の個別リセットを呼ぶ |
| 選択肢C | リセットのたびにWireMockコンテナを再起動する |
| 決定 | 呼び出し手順は選択肢A。ただし毎回FR-709の確認を行い、確認が失敗したらテストを失敗させる |
| 理由 | 1回の呼び出しで足りるかは実機でしか確認できない。確認を必須にすれば、前提が外れても検知できる |

リポジトリの読み取りだけでは、次の3点を確定できない。推測で確定せず、実機確認に回す。

| 未確認の事実 | 確認の手順（plan以降） |
| --- | --- |
| `POST /__admin/reset`がファイル由来のマッピングを復元するか | `normal-case.json`相当の応答を、リセット後に`GET /__admin/mappings`の件数と`/api/users/123`の応答で確かめる |
| 同じ呼び出しで、リクエストジャーナルが空になるか | リセット後の`GET /__admin/requests`の件数が0であることを確かめる |
| 同じ呼び出しで、シナリオ状態が`Started`に戻るか | `error-500-then-200`を1回呼んで`Succeeded`へ進めた後にリセットし、`GET /__admin/scenarios`の全状態が`Started`であることを確かめる |

確認でいずれかが満たされなかった場合の対処は次のとおり。

| 状況 | 対処 |
| --- | --- |
| マッピングが復元されない | マッピングだけの再読み込み用エンドポイントを追加で呼ぶ（名前と挙動は3.13.1の管理API仕様と実機で確認する） |
| ジャーナルが空にならない | ジャーナル削除用のエンドポイントを追加で呼ぶ（同上） |
| シナリオ状態が戻らない | シナリオ状態のリセット用エンドポイントを追加で呼ぶ（同上） |
| 追加呼び出しでも戻らない | 選択肢Cに切り替える。ただしM08のE2Eが遅くなるため、ユーザーに確認する |

補足は次のとおり。

- 管理APIで追加した（ファイルに無い）マッピングはリセットで消えることも、同じ手順で確かめる。
- FR-709の「ファイル由来の件数」は、`mappings/*.json`のファイル数と一致させる。1ファイル1マッピングを維持するため
  （Q-705）、件数の計算が単純になる。`.gitkeep`は数えない。
- 状態漏れの対照実験（完了条件の4項目目）は、`error-500-then-200`をリセットなしで2回続けて呼び、
  2回目が初回から200になることを示す。次にリセットを挟むと、初回が500に戻ることを示す。
- 確認は`unit`ではなく`smoke`で行う。管理APIの応答の形（件数のフィールド名など）は実機の応答で確認してから、
  パース方法を固定する。

spec.mdの更新箇所は次のとおり。

| 更新箇所 | 変更 |
| --- | --- |
| FR-707 | 「ファイル置換」を削り、「WireMockの管理API」に限る（Q-704）。具体的な呼び出し列はplanで確定する旨を添える |
| FR-709 | 確認の手段（マッピング一覧、ジャーナル、シナリオ一覧）と、不一致時に終了コード非ゼロで停止することを具体化する |
| 8章 | Q-703は「plan以降の実機確認」に分類を移し、上の表の3項目を検証手順として残す |

  ここでは確定しない。
- マッピングの追加と変更の反映は、WireMockの再起動か管理APIでの再読み込みが要るかを実機で確認する。

| コピーを破棄し、リポジトリの`git status`が実験の前後で変わらないことを確かめる | リポジトリを汚していない |

この確認は手動で一度だけ行い、`smoke`には入れない。`smoke`はリポジトリのファイルを書き換えない。

### Q-705 状態を持つシナリオのファイル形式と検査の改修範囲

| 項目 | 内容 |
| --- | --- |
| 選択肢A | 状態ごとに1ファイルとし、同じ`scenarioName`を持つ複数ファイルで1シナリオを構成する。M03の検査は変えない |
| 選択肢B | WireMockの複数スタブ形式（`mappings`配列）で1シナリオ1ファイルにし、M03の検査を拡張する |
| 選択肢C | 「500の後に200」をWireMock以外（クライアント側）で再現する |
| 決定 | 選択肢A |
| 理由 | M03の検査と契約を一切変えず、1ファイル1マッピングの規約を保てる。ファイル数と件数の対応が単純になる |

選択肢B、Cを採らない理由は次のとおり。

| 選択肢 | 採らない理由 |
| --- | --- |
| B | M03の検査が`mappings`配列を拒否するため、M03の検査を書き換える必要がある。件数の数え方も変わる |
| C | Issueが「WireMockシナリオの切り替え」を求めており、M06が別途としたリトライ成功の再現にもならない |

「500の後に200」の構成は次のとおり。

| ファイル | 内容 |
| --- | --- |
| `mappings/error-500-then-200-1.json` | `GET /api/error-500-then-200`、`scenarioName`は`error-500-then-200`、`requiredScenarioState`は`Started`、`newScenarioState`は`Succeeded`。500と`error-500.json` |
| `mappings/error-500-then-200-2.json` | 同じ`method`と`urlPath`、同じ`scenarioName`、`requiredScenarioState`は`Succeeded`。`newScenarioState`は付けず、200と`success.json` |

この構成で、初回が500、2回目以降は200のまま維持される。`__files/`は既存のものを再利用し、新しい本文は足さない。

M03の検査との整合は次のとおり。

- 2ファイルとも、トップレベルに`request.method`、`request.urlPath`、`response.status`を持つため、M03の検査を通る。
- `scenarioName`、`requiredScenarioState`、`newScenarioState`は、M03の検査が見ないキーである。
- M03の検査は`/api/error-500-then-200`がマッピング一覧に含まれることを要求しない。M07側で追加する。

M07の`unit`で追加する静的検査は次のとおり。

| 検査 | 内容 |
| --- | --- |
| 状態の網羅 | `scenarioName`を持つグループに、`requiredScenarioState`が`Started`のスタブがちょうど1つある |
| 遷移の到達性 | `newScenarioState`の値は、同じグループのどれかの`requiredScenarioState`に現れる |
| 宛先の一致 | 同じグループのスタブは同じ`method`と`urlPath`を持つ |
| 名前の一致 | 同じ`scenarioName`のスタブは同じ`name`を持つ |
| 部分指定 | `requiredScenarioState`を持つのに`scenarioName`が無いスタブを拒否する |

これらの検査はM03の検査とは別に`tests/m07-scenario-isolation.sh`の`unit`に置き、M03のファイルは変更しない。

spec.mdの更新箇所は次のとおり。

| 更新箇所 | 変更 |
| --- | --- |
| 2章、FR-711 | 「1つのJSONファイル」を「JSONファイル単位」に直す。状態を持たないシナリオは1ファイル、状態遷移を持つシナリオは状態ごとに1ファイルと明記する |
| FR-703 | 2ファイル構成（上の表）を追記する |
| FR-709 | 「ファイル由来の件数」を「`mappings/*.json`のファイル数」と定義する |
| NFR-701 | 1ファイル1マッピングの規約を維持する旨を足す |
| 6章（対象外） | 「複数スタブ形式（`mappings`配列）とM03の検査の拡張」を追加する |

### Q-707 429シナリオの形

| 項目 | 内容 |
| --- | --- |
| 選択肢A | 既存の`/api/ratelimit`（常に429、`Retry-After: 2`）を流用する |
| 選択肢B | 429の後に200を返す型を新設する |
| 選択肢C | 両方を用意する |
| 決定 | 選択肢A |
| 理由 | FR-704は「429と`Retry-After`を返す」だけを求める。Issueの対象も「429」であり、新設はファイルと検査を増やす |

細則は次のとおり。

- M06の`Retry-After`尊重は、`ratelimit-429`をTest Clientで呼び、
  診断ログの待機時間（`Retry-After: 2`に由来）と`wiremock_count`で確認する。
  Test Clientの429リトライ回数の既定は3回（総試行4回）であり、最終結果は`retries_exhausted`となる。
- 「429の後に200」が要るかどうかは、M08のE2E設計で判断する。必要ならFR-711の手順で1つ足すだけで済む。
- `Retry-After: 2`は変更しない（M03の契約）。

### Q-709 検査入口とモード

| 項目 | 内容 |
| --- | --- |
| 選択肢A | `tests/m07-scenario-isolation.sh`に`unit`と`smoke`の2モード（既定は`smoke`）を持たせる |
| 選択肢B | `smoke`だけにする |
| 選択肢C | 名前の解決、リセット、検査をそれぞれ別のテストファイルにする |
| 決定 | 選択肢A |
| 理由 | M06と同じ構成で、読む人が迷わない。静的検査はDockerなしで速く、実機の検査は`smoke`に集められる |

各モードの内容は次のとおり。

| モード | 内容 |
| --- | --- |
| `unit` | Dockerを使わない。名前の解決（未定義の名前は終了コード2）、名前の形式と重複、状態を持つグループの静的検査（Q-705）、追加手順の検査（下記） |
| `smoke` | `unit`に続けてComposeを起動し、リセットと確認、対照実験（Q-703）、「500の後に200」の通し実行、4シナリオの応答、失敗経路の回収を確かめる |

追加手順の検査は、`unit`で`wiremock-scenarios/`を`mktemp -d`の一時ディレクトリへコピーし、
手順どおりに1ファイルを足して、名前の解決と静的検査が通ることを確かめる。リポジトリのファイルは書き換えない。

失敗経路の検査は次のとおり。

- アサーション失敗、`INT`、`TERM`で、`docker-compose ps -a -q`が空になり、一時ディレクトリが残らないことを確かめる。
- 終了コードが元の失敗を保つことを確かめる（`INT`は130、`TERM`は143を期待し、plan以降で実機確認する）。
- 検査自身を失敗させるための注入は、環境変数ではなく検査内のサブシェルで行い、本番のスクリプトに分岐を持ち込まない。

共通の取り決めは次のとおり。

- POSIX shで書く（NFR-704）。名前の解決のためのJSON解析はM03と同じホストの`python3`を使い、新しい依存を足さない。
- 同じ検査を連続で2回実行して同じ結果になることを`smoke`の最後に確かめる（NFR-705）。
- `scripts/quality-gate.sh`への登録が要るかは、plan以降に既存の登録方法（M06の扱い）を読んで確認する。

| 判断 | 影響 | 推奨既定 |

| 追加手順の単位を「1つのJSONファイル」から「JSONファイル単位」へ緩める | 状態を持つシナリオは複数ファイルになる。spec.mdの文言がIssue #7に合う | 緩める（状態ごとに1ファイル） |
| M03の4ファイル（`normal`、`error-429`、`delay-100ms`、`delay-5000ms`）に`name`を1行足す | M03のファイルを変更する。応答の契約は変わらない | 足す（複製して新しいパスを作らない） |
